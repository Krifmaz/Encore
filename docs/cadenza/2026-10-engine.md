# Cadenza engine work for Encore 0.27 – brief for the Cadenza agent

Written Oct 18, 2026 in the Encore repo (docs/cadenza/2026-10-engine.md). It is the prompt for an agent working in
the **Cadenza repo** (github.com/Krifmaz/cadenza). Encore never edits that repo; everything below is done there,
and Encore then moves its pins (`cadenza` in the desktop app, `cadenza-dsp` in the server and the phone) to the
new rev. The brief is self-contained: it says what Encore sends, what Encore reads, what is wrong on the owner's
machine, and what to change. File names refer to the Cadenza tree at rev `a8218b8` ("Embeddable player: bearer
tokens, stoppable Encore link, full engine description and settings over Encore", Oct 14, 2026), the rev the
Encore desktop app pins today. If HEAD has moved, read the files again before changing them; the shape is the same.

Rules for the agent:
- Plain words everywhere (log lines, errors, JSON labels). No exclamation marks.
- No behaviour change for anything not named here: the config keys, the `GET/PUT /api/settings` shape, the CLI,
  the endpoint protocol and the keys Encore already reads (section 3) keep working. New keys are added, old ones
  are not renamed.
- Every item gets a test that runs without a DAC (the null output, a local HTTP server, files made in the test).
  `cargo test`, `cargo clippy -- -D warnings` and `cargo fmt --check` stay clean on Linux; the Windows and macOS
  backends must at least build (`cargo check --features wasapi` on Windows CI, `--features coreaudio` on macOS CI).
- `cadenza` and `cadenza-dsp` are published from one workspace and Encore bumps both pins to the same rev, with a CI
  check that the three Encore Cargo.toml revs match. Keep the two crates building together; if a `cadenza-dsp` API
  changes (section 4.L adds one field), say so in the report, because the Encore server and the phone build it too.
- Report back (section 7) with the rev, the new JSON keys and anything that could only be tried on the hardware.

## 1. The setup this has to fix

The owner's desktop: Windows, NVIDIA RTX 3070, USB → **Singxer SU-2** (USB to I2S / S/PDIF / AES DDC) → **Fosi
Audio ZD3** (ES9038Q2M). The ZD3 is also plugged in directly over USB at times. The ZD3 takes **DSD256 at most**.
Cadenza runs inside the Encore desktop app (`cadenza::embed::EmbeddedPlayer`, WASAPI feature, CUDA feature) and is
controlled from Encore's Settings → Playback → Cadenza engine card, which renders `engine_description()`.

Seen on screen, with the code path behind each:

1. **Exclusive is ticked, but the status line says "wasapi · … · Shared".** The tick comes from
   `engine.exclusive_wanted` (backend is not cpal/null); the word comes from `engine.exclusive`, which is
   `Status.output_exclusive: bool` – `false` until `Worker::ensure_output` has opened the device (worker.rs ~553),
   and `false` for good when `open_backend` failed and the worker silently switched to the null output (worker.rs
   ~533–541: "using the null output"). So "Shared" is shown both before the first play and after a failed open, and
   in the second case there is no sound and no visible error beyond `engine.error`. Sections 4.E, 4.F and 4.G.
2. **DSD512 stayed selected on the ZD3.** `encore::state::dsd_rates(&status.output_dsd)` lists every DoP rate up to
   DSD1024 while the capabilities are unknown (`DsdCaps::NONE` until the output is opened), and `validate` never
   looks at the device. Sections 4.H and 4.I.
3. **`…/tracks/58742/stream: decode: unsupported feature: core (codec):unsupported codec` on an Opus file.**
   Symphonia 0.5 (features `all`) has the Ogg demuxer and recognises the Opus mapping (`CODEC_TYPE_OPUS`), but ships
   no Opus decoder, so `get_codecs().make()` fails in `decode/mod.rs` (`Decoder::open`). The error is set in
   `Worker::pump` and the worker moves on to the next track; an Opus album is skipped track by track. Sections 4.A
   and 4.C (the server now sends FLAC instead when the engine says it has no Opus decoder).
4. **Position stuck at 0:00.** Several candidates, section 4.N.

## 2. What Encore 0.27 does on its side (so you know the counterpart)

- The Encore **server** (0.27.0, `server/src/routes/library.rs`) negotiates codecs on `GET
  /api/library/tracks/{id}/stream`: a client that sends `X-Encore-Decoders` gets the original when the file's codec
  is in its list and a lossless FLAC transcode otherwise, labelled in `x-encore-stream`. Section 3.1 has the exact
  contract. The same decision is readable at `GET /api/library/tracks/{id}/info`.
- The Encore **desktop app** is being rewritten in Iced (pure Rust). It links `cadenza` in directly, no web view and
  no bridge, and renders the Playback card and the signal path from the JSON this brief defines (section 3.2),
  calling the embed API of section 4.M: describe, set, outputs, codecs, test sound, play, control, subscribe. The
  current Tauri app keeps using `EmbeddedPlayer::start / connect / disconnect / status_json / engine().play_queue /
  shutdown` for one more release, so those stay.
- Encore's Settings → Playback switch "Play through Cadenza on this device" is off by default; with it on, the engine
  is this device's own output path (not a device in the device picker). A standalone `cadenza serve` on the LAN stays
  a device Encore controls, with the same JSON.
- Encore shows only what the engine reports. There is no guessing on the Encore side: if the engine does not say
  why exclusive failed, the user sees nothing useful. That is why the words in section 4.G matter.

## 3. The contract between Encore and the engine

### 3.1 Streams (Encore server 0.27)

Request: `GET {server}/api/library/tracks/{id}/stream` with the auth header the link already sends
(`Authorization: Bearer <app token>` or `Cookie: encore_session=…`; see `encore/client.rs` `stream_headers()`), plus:

- `X-Encore-Decoders: flac,mp3,aac,alac,opus,vorbis,wav,aiff,dsf,dff` – the codecs this build decodes, comma
  separated, lower case. Also understood by the server: `wavpack`, `ape`; `dsd` stands for `dsf,dff`; `ogg` for
  `vorbis`. The same list may go as `?codecs=` on the URL for a client that cannot send headers; the header wins when
  both are given. An empty list counts as "nothing said" (the server then behaves as for a browser).
- `?t=<seconds>` (a float, e.g. `t=93.50`): start a **converted** stream at that position. The server runs
  `ffmpeg -ss`; on an original (Range) stream the parameter is ignored. Section 4.D uses this for seeking.

Response headers:

- `x-encore-stream` – one word for what the body is. Vocabulary (Encore 0.27.0, routes/library.rs):
  - `original` – the file, byte for byte. Range requests work (206, `Accept-Ranges: bytes`, `Content-Length`).
    Content types: `audio/flac`, `audio/mpeg`, `audio/mp4`, `audio/aac`, `audio/ogg` (Vorbis and Opus),
    `audio/wav`, `audio/webm`, `audio/aiff`, `audio/x-dsf`, `audio/x-dff`, `audio/x-wavpack`, `audio/x-ape`, else
    `application/octet-stream`.
  - `flac-fallback` – lossless FLAC made on the fly because the client's decoder list does not cover the file's
    codec (the owner's Opus case). `ffmpeg … -c:a flac -compression_level 0 -f flac pipe:1`, same sample rate and
    bit depth as the source (DSF/DFF are decoded to 24-bit 176.4 kHz PCM first), `Content-Type: audio/flac`,
    **streamed: no Content-Length, no Range, and the FLAC STREAMINFO has no total-samples count and no seek table.**
  - `flac` – the same FLAC conversion, made because a browser cannot play the format or `transcode=1` was asked for.
    Same properties as `flac-fallback`. The engine never asks for it but should treat it the same way.
  - `aac-<kbps>`, `opus-<kbps>` – lossy streams a browser asked for (`q=aac|opus`). The engine never asks for them.
  - `cadenza-<rate>` – upsampled on the server by Cadenza (`dsp=1`). The engine never asks for it.
  A FLAC file is always served as `original` when a decoder list is given (the fallback would be FLAC too).
  `x-transcoded` carries the same word on converted streams (older clients read it); ignore it.

`GET /api/library/tracks/{id}/info` with the same header (or `?codecs=`) answers the file's `codec`, `sample_rate`,
`bit_depth`, `channels`, `bitrate`, `duration`, `lossless`, plus `stream: {kind, codec, reason}` where `kind` is the
`x-encore-stream` word the stream would carry, `codec` the file's codec in the words of the decoders list and
`reason` plain words such as "the client has no Opus decoder" (null for the original). Encore's UI calls this itself
with the engine's published decoder list (section 3.2 `engine.decoders`) to write the signal path row "transcoded to
FLAC because the engine has no Opus decoder"; the engine does not need to call it.

### 3.2 The state Encore reads

Every 2 s the link posts `{id, name, state}` to `POST /api/remote/heartbeat` (`encore/mod.rs` heartbeat_loop; the
state is built by `encore/state.rs` `heartbeat_state_as`). The desktop app will read the same object directly
(section 4.M). Keys Encore reads today and must keep their meaning:

- top level: `id, title, artist, album, album_id, format, cover, playing, paused, position, duration, volume, index,
  queue[]`.
- `signal: {label, transport, output_rate, bitperfect, stages: [{name, detail}]}` – the signal path dialog.
  `transport` is hard-coded `"original"` today; section 4.C makes it the server's word.
- `engine: {…}` from `engine_description()`: `name, version, embedded, host, error, output, exclusive,
  exclusive_wanted, outputs: [[id,label]], output_id, bitperfect, filter, filters, dither, dithers, rate, rates,
  bits, bits_list, output_mode, output_modes, dsd: {rate, rates, modulator, modulators, packing, packings, gain_db,
  oversampling, oversamplings, device}, headroom_db, soft_clip, gpu, gpu_available, gpu_in_use, gpu_name, matrix,
  matrix_presets`.

New or changed keys this brief adds (Encore's Iced app is written against this list, so keep the names):

| key | type | meaning |
|---|---|---|
| `engine.exclusive` | `true` / `false` / `null` | `null` until the output has been opened (4.F). Encore shows "Exclusive", "Shared" or "not opened yet". |
| `engine.format` | `{wanted: string\|null, actual: string\|null, note: string\|null}` | The format the chain asked for and the one the device opened, as `OutputFormat::label()` strings ("24-bit 352.8 kHz", "DSD256 (DoP)"); `note` says why they differ (4.F). |
| `engine.device` | `DeviceInfo` JSON or `null` | The probed capabilities of the configured output: `backend, id, name, rates, bits, channels, default, exclusive, dsd: {dop, native, max_rate}`, plus `probed: bool` (4.H). |
| `engine.adjustments` | `[{key, wanted, used, reason}]` | What `validate` clamped, e.g. `{"key":"dsd_rate","wanted":"dsd512","used":"dsd256","reason":"the device stops at DSD256"}` (4.I). Empty when nothing was clamped. |
| `engine.rejected` | `{set: {…}, reason}` or `null` | The last `engine {set}` patch the engine refused and why (4.I, 4.J); cleared by the next accepted patch. |
| `engine.link` | `"usb"` / `"i2s"` / `"spdif-coax"` / `"spdif-optical"` | `output.link` (4.K). |
| `engine.links` | `[[id, label]]` | The four choices with labels (4.K). |
| `engine.decoders` | `[string]` | The list sent as `X-Encore-Decoders` (4.B, 4.C). |
| `engine.latency_seconds` | number | The chain's processing latency, 0 while stopped (4.N). |
| `signal.transport` | string or `null` | The `x-encore-stream` word of the current track (4.C); `null` for a local file or before the response came. |
| `engine.error` | string or `null` | Unchanged key, new wording rules (4.E, 4.G): the whole sentence a user needs, nothing of the HRESULT. |

### 3.3 Commands

Commands arrive in the heartbeat answer (`commands: []`) and over `GET /api/remote/events?device=…` (SSE), both run
through `encore/commands.rs` `run()`: `play_queue {tracks, index, position}`, `enqueue`, `play_next`, `toggle, play,
pause, stop, next, prev, seek {seconds}, volume {level}` and `engine {set: {…}}`. The `set` object is applied by
`patch_settings` key by key, checked with `api::validate`, and today a patch that does not validate is dropped with
only a log line (`apply_engine_settings`). Tracks in `play_queue` are `{id, title, artist, album, album_id, format,
duration}`; 4.L adds `gain_db`. Keep every key `patch_settings` accepts; 4.K adds `link`.

## 4. The work

### 4.A Opus decoding

Add an Opus decoder so `.opus` and `.ogg` (Opus mapping) files play, in `decode/mod.rs` through Symphonia's codec
registry: implement `symphonia::core::codecs::Decoder` for Opus and register it in a `CodecRegistry` that also holds
`symphonia::default::register_enabled_codecs`; `Decoder::open` uses that registry instead of
`symphonia::default::get_codecs()`. The Ogg demuxer already delivers the packets and the `OpusHead`/`OpusTags`
extra data (`codec_params.extra_data`). Opus in Matroska/WebM goes through the same decoder if the MKV demuxer
hands it packets; test Ogg first, WebM if cheap.

Implementation choice, in this order of preference: a complete pure-Rust Opus decoder crate if one exists at full
quality (check crates.io and Symphonia's development branch for `symphonia-codec-opus`); otherwise libopus through
the `opus` or `audiopus` bindings with the C library built from source by the `-sys` crate (vendored, no system
package), making sure the Windows, macOS and Linux CI builds have what that needs (cmake) and that the desktop
build with features `wasapi, cuda` still links. Say in the report which one you took and why.

Opus details that must be right, with a test for each:

- Decoded sample rate is 48 000 Hz for every Opus stream; `TrackInfo.rate` = 48 000, `bits` = 0 (lossy, so
  `pcm_input()` reports 24), `codec` = `OPUS` through `normalise_codec`. The `OpusHead` `input_sample_rate` is
  information only. The signal path shows `Opus 48` as the source.
- Pre-skip: drop the first `pre_skip` samples of the stream (from `OpusHead`), also after a seek to the start.
- Output gain: apply the `OpusHead` output gain (Q7.8 dB) in the decoder, or document that it is ignored on purpose.
- End trimming: the last page's granule position says how many samples are valid; do not play the padding.
- Seeking: Symphonia's Ogg demuxer seeks by granule position; after a seek, decode and discard up to the target
  (the demuxer gives the page start) and reset the decoder state, or there will be a click.
- Channels: 1 and 2 at least; multichannel (channel mapping family 1) decodes or is refused with a plain message.
- A 4-minute Opus file in `pump` must not be slower than real time on a small CPU (log the decode speed once).

Test material: make the files in the test with `ffmpeg` when it is on PATH (`-c:a libopus -b:a 128k`), skip the test
with a clear message when it is not, as other tests do. Compare against the same file decoded by ffmpeg to
`s16le` with a tolerance (Opus decoders are not bit-exact across implementations).

### 4.B Verify AAC, ALAC, WavPack, APE, DSF, DFF, and publish the decoder list

For each: a file made with ffmpeg in the test (`aac` in `.m4a`, `alac` in `.m4a`, `wavpack` in `.wv`, `ape` in
`.ape` – ffmpeg has no APE encoder, so APE is "decode a checked-in 2-second sample or skip", `dsf` from a PCM source
with `-c:a dsd_lsbf_planar`, `dff` with `-c:a dsd_msbf` if the build has them, otherwise the writers in
`decode/dsd.rs`), opened through `TrackDecoder::open`, decoded to the end, position and duration checked, one seek.

Expected results today: AAC and ALAC decode (Symphonia `aac`, `alac`), DSF and DFF decode through `decode/dsd.rs`
(DST-compressed DFF is refused by design, keep that, the message is already plain), **WavPack and APE do not decode**
(Symphonia 0.5 has neither). Do not add WavPack or APE decoders in this round unless a pure-Rust crate makes it a
small job; what does not decode is simply left out of the published list and the server sends FLAC for it.

Add `decode::supported_codecs() -> Vec<&'static str>` that returns, in the server's words, exactly what this build
decodes: built from the codec registry (`flac, mp3, aac, alac, vorbis, opus, wav, aiff, pcm` as applicable, `wav`
and `aiff` meaning the RIFF/AIFF readers) plus `dsf, dff` from the DSD reader. Lower case, the server's spelling
(section 3.1). A test asserts the list contains `opus` after 4.A and never contains `wavpack` or `ape` while they
do not decode. Publish it as `engine.decoders` in `engine_description()`.

### 4.C Send `X-Encore-Decoders`, set `signal.transport`

- `encore/client.rs` `stream_headers()` adds `("X-Encore-Decoders", supported_codecs().join(","))` next to the auth
  header. Test: the existing `stream_sends_bearer` style test sees the header.
- `decode/source.rs` `HttpSource` keeps the response headers it cares about from the **first** response of a source:
  `content_type` (exists) and a new `stream_label: Option<String>` = `x-encore-stream`. Expose it through
  `Source`/`Decoder`/`TrackDecoder` as `transport() -> Option<String>` (None for a local file or when the header is
  missing).
- `engine/worker.rs` records it per current track and `Status` gets `transport: Option<String>`;
  `encore/state.rs` writes `signal.transport` from it instead of `"original"`. The `state_has_the_fields_encore_reads`
  test changes accordingly (a `Source::Path` track gives `null`).
- Log one line per track with the transport word and the content type, so a log shows "flac-fallback" at once.

### 4.D Seek on streams without Range support by reopening with `&t=`

A `flac` / `flac-fallback` stream is a pipe: 200 without `Accept-Ranges`, no `Content-Length`, STREAMINFO without a
total-samples count. `HttpSource::is_seekable()` is false there, Symphonia refuses the seek, and the duration is
unknown. Do this:

- `Source::Url` gets `seek_param: Option<String>` (serde default None; `track_from_encore` sets `Some("t")` for
  Encore tracks). When `TrackDecoder::seek(seconds)` fails because the source is not seekable and `seek_param` is
  set, reopen the same URL with `&t=<seconds>` (or `?t=` when the URL has no query; replace an existing `t=`),
  rebuild the Symphonia probe and decoder, and keep a `time_offset = seconds` that `position_seconds()` adds. The
  original (Range) streams keep seeking by bytes as today; the reopen path is only for non-seekable sources.
- `duration`: the decoder has none for these streams; `Worker::publish` already falls back to `Track.duration`
  (worker.rs ~1010), which `track_from_encore` fills from Encore. Keep that, and make `TrackDecoder::duration()`
  return the track's duration to `report_play` as well, so plays are reported for FLAC fallbacks too.
- Prefetch (`PREFETCH_SECONDS`, `maybe_prefetch`) works unchanged: the next track opens at `t=0`.
- Test with a small HTTP server in the test (the pattern in `encore/client.rs` tests) that answers a WAV or FLAC
  body with 200 and no Range support, and checks that a seek to 2 s reopens with `t=2.00` in the query and that
  `position_seconds()` reports ≥ 2 afterwards.

### 4.E No null-output fallback

`Worker::ensure_output` (worker.rs ~525–560): when `open_backend` fails, set `self.error` to the plain words of
4.G, leave `self.output = None`, return `Err`. `build_chain` then fails, `start_index` calls `fail("cannot play …")`,
the state is Stopped and `runs_finished` grows. Nothing is written to a null device; the UI shows the error and the
transport shows stopped instead of a progress bar that moves without sound. An explicit `backend = "null"` keeps
working (tests, headless boxes). Tests: a config with `backend = "nonsense"` or `device = "no such device"` leaves
the status stopped with the error set, and `output_exclusive` stays `null` (4.F).

### 4.F `exclusive` unknown until opened; format wanted next to format in use

- `Status.output_exclusive: Option<bool>` (serde default None): `None` until `open()` has returned, then
  `out.exclusive()`. Closing the output (settings change, 4.H) sets it back to `None`. JSON: `engine.exclusive` is
  `true`, `false` or `null`. Keep `exclusive_wanted` as it is.
- `Status.output_wanted: Option<OutputFormat>` next to `output_format`: what `build_chain` asked for before
  `choose_rate` / `choose_dsd` stepped it down, or what the device changed in `open()`. `engine.format = {wanted,
  actual, note}` with the labels, `note` filled when they differ: "DSD512 asked, DSD256 played: the device stops at
  DSD256", "352.8 kHz asked, 176.4 kHz played: the device does not take 352.8 kHz", "the device opened 32-bit
  words for 24-bit samples" (that one is harmless; say so). `engine.output` keeps its current text.
- Tests on the null output: wanted DSD2048 → actual DSD1024 with a note; a wanted rate the null device supports →
  no note; before any play, `exclusive` is `null` and `format.actual` is `null`.

### 4.G WASAPI results in plain words

`output/wasapi_backend.rs`: `open()` maps every failure to an `OutputError` whose `Display` is the sentence the
user needs. The wasapi crate returns `WasapiError::Windows(windows_core::Error)` for COM failures; read the HRESULT
(`e.code()`) and match (values from audioclient.h; verify them against the header you build with):

| HRESULT | name | words |
|---|---|---|
| `0x8889000A` | `AUDCLNT_E_DEVICE_IN_USE` | "Exclusive mode failed: another program is using <device> (close it, or stop its exclusive mode)" – plus the holder's name when 4.G.2 finds one |
| `0x8889000E` | `AUDCLNT_E_EXCLUSIVE_MODE_NOT_ALLOWED` | "Exclusive mode failed: Windows does not allow programs to take exclusive control of <device>. Sound settings → <device> → Properties → Advanced → tick 'Allow applications to take exclusive control of this device'" |
| `0x88890008` | `AUDCLNT_E_UNSUPPORTED_FORMAT` (and `is_supported_exclusive_with_quirks` failing) | "<device> does not take <format label> in exclusive mode" (today's `OutputError::Unsupported` text, reworded) |
| `0x88890004` | `AUDCLNT_E_DEVICE_INVALIDATED` | "<device> was unplugged or disabled" |
| `0x88890019` | `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED` | not an error for the user: re-initialise with the aligned buffer size the client reports (`get_buffer_size` → recompute the period), as the WASAPI documentation prescribes |
| `0x88890010` | `AUDCLNT_E_SERVICE_NOT_RUNNING` | "the Windows Audio service is not running" |
| `0x8889000F` | `AUDCLNT_E_ENDPOINT_CREATE_FAILED` | "Windows could not open <device> (endpoint creation failed); try unplugging and plugging it in" |
| anything else | | "<device>: Windows error 0x… while <step>" where `<step>` is `opening`, `checking the format`, `starting the stream` |

Add `OutputError::InUse { device, holder: Option<String> }` and `OutputError::NotAllowed { device }` so the engine
and Encore can tell these apart from a format problem without parsing text; `Display` gives the sentences above.
Also map the other backends' equivalents where they exist (ALSA `EBUSY` → in use; CoreAudio hog refusal → in use)
with the same words, so the engine wording is the same on every OS.

4.G.2 Holder detection, best effort (Windows): when open fails with `DEVICE_IN_USE`, enumerate the endpoint's audio
sessions (`IMMDevice::Activate<IAudioSessionManager2>` → `GetSessionEnumerator` → `IAudioSessionControl2::GetProcessId`
for sessions in state Active) and name the process images (`QueryFullProcessImageNameW`), excluding our own pid. The
wasapi crate wraps `IAudioSessionManager`; use the `windows` crate directly for the rest. An empty list gives
"another program"; a list gives "another program is using <device>: foobar2000.exe". Encore shows the string as it
is. The event-driven exclusive stream of another process does not always show up as a session, so this stays best
effort and must never fail the open path itself.

4.G.3 Where the words go: `Worker.error` (so `engine.error`), the log at `error` level once (not every period), and
`Status.output_exclusive` stays `None` (4.F). `write()` failures mid-stream (`EventTimeout` from `wait_for_event`,
`DEVICE_INVALIDATED` when the DAC is unplugged) stop playback with the same wording instead of logging every period
(worker.rs `write_out` sets `self.error` today but keeps pumping).

### 4.H Probe and publish device capabilities at start and on device change

Today `output_rates`, `output_dsd` and the `rates` / `dsd.rates` lists are filled in `ensure_output`, which runs on
the first play, so until then the UI offers every rate. Change:

- A `probe_device(backend, device) -> Result<DeviceInfo, OutputError>` in `output/mod.rs` that finds the device,
  asks `supports()` for `STANDARD_RATES` at 16/24/32 bits and `dsd_caps()`, without opening a stream (WASAPI
  `IsFormatSupported`, ALSA `hw_params` test, CoreAudio stream format queries). It is the same work
  `list_devices()` does for one device; share the code.
- The worker runs it when it starts (with the configured backend and device), whenever `settings.output.backend`
  or `settings.output.device` changes in `update_settings` (today, while stopped, `output = None` is all that
  happens), and after an open failed (the capabilities may explain the failure). The result fills `output_rates`,
  `output_dsd`, a new `Status.device: Option<DeviceInfo>` and `engine.device` (with `probed: true`); a failed probe
  publishes `device: {…, probed: false}` and the error.
- Probing is synchronous on the worker thread (WASAPI COM objects live there); log how long it took. The
  `outputs()` list cache (30 s) in `encore/state.rs` stays.
- `encore/state.rs`: `rates` and `dsd.rates` / `dsd.packings` are derived from the probe, so they are right before
  the first play. With `DsdCaps::NONE` after a successful probe, the DSD list is empty and `output_mode = dsd` is
  refused (4.J), instead of "unknown lists everything".
- Test with the null output (which "probes" as the ideal device): after `Engine::start`, before any play, `status()`
  has `output_rates` filled and `device.probed == true`.

### 4.I Clamp `rate` and `dsd_rate` in `validate`; report what was clamped

`api::validate(settings)` becomes `validate(settings, device: Option<&DeviceInfo>, link: Link) -> Result<Vec<Adjustment>,
String>` with `Adjustment {key, wanted, used, reason}`; the old signature stays as a wrapper for the HTTP API and the
tests (`device: None`). With a device:

- `output.rate = Fixed(r)` not in `device.rates` → the highest rate in `device.rates` of the same family (44.1 or 48
  k) that is ≤ r, else `auto`; reason "the device does not take <r> kHz".
- `dsp.dsd_rate` above `device.dsd.max_rate` → the highest catalogue rate the device takes (`choose_dsd` logic,
  honouring packing); reason "the device stops at DSD256". `dsd_packing = native` with no native layout → `dop`
  with a reason. DoP needing a PCM rate above `device.rates` → the next lower DSD rate.
- The 4.K link ceiling is applied the same way, with "S/PDIF carries at most 192 kHz" / "S/PDIF carries at most
  DoP64" as the reason.
- The adjustments are applied to the settings that reach the worker (so the file and the UI agree), published as
  `engine.adjustments`, and shown by Encore as "playing DSD256 (device limit)". They are recomputed on every
  settings change and every probe (4.H): a DAC change can lift a clamp.
- `encore/commands.rs` `apply_engine_settings`: a patch refused by `validate` is published as `engine.rejected =
  {set, reason}` and logged; an accepted one clears it. The reason text is the one the user sees.
- Tests: a device with `rates = [44100, 48000, 88200, 96000, 176400, 192000]` and `dsd.max_rate = DSD128` clamps
  `rate = 352800` to 176400 and `dsd_rate = dsd512` to dsd128 with reasons; the null device clamps nothing;
  `rejected` is set and cleared.

### 4.J Reject `output_mode = dsd` on a shared backend

A shared backend (`cpal`, and any `Output` whose `exclusive()` is false) mixes and resamples; DoP markers through a
mixer are noise. `validate` refuses `output_mode = dsd` and `dsd_passthrough` into such a backend with "DSD output
needs exclusive mode: turn on Exclusive (WASAPI) first" and the patch is reported through `engine.rejected`. The
worker's `passthrough_target` also requires `out.exclusive()`, so a DSF file on a shared backend goes DSD → PCM. The
null output keeps `exclusive() == true` so the DSD tests stay as they are. Encore greys the DSD mode with the reason
when exclusive is off.

### 4.K `output.link`

New config key `[output] link = "usb"` with values `usb | i2s | spdif-coax | spdif-optical` (serde default `usb`;
unknown values are a config error with the four names in the message). It describes the cable **after** the device
Windows sees: the owner's SU-2 is a USB DDC whose USB interface reports its own limits, while the DAC behind it is
fed over I2S or S/PDIF. Ceilings:

- `usb`, `i2s`: no ceiling beyond the device's own capabilities.
- `spdif-coax`, `spdif-optical`: PCM at most 192 kHz / 24-bit; DSD only as DoP64 (DSD64 in 176.4 kHz frames); no
  native DSD. Optical is often 96 kHz in practice, but the spec allows 192 kHz; keep 192 kHz and let the user pick
  a lower fixed rate.

Apply the ceiling in `choose_rate` (cap `max_rate`), `choose_dsd` (cap the rate, force DoP), `dsd_rates()` /
`rates` in the description, and `validate` (4.I, with a reason). `patch_settings` accepts `link`; the description
publishes `engine.link` and `engine.links = [["usb","USB"],["i2s","I2S"],["spdif-coax","S/PDIF coax"],
["spdif-optical","S/PDIF optical"]]`. The CLI gets `--link`. Tests: with `spdif-coax` the null device's auto rate
for a 44.1 k source is 176.4 kHz and `dsd_rate = dsd256` is clamped to dsd64 DoP with the reason.

### 4.L Per-track `gain_db`

`engine::Track` gets `gain_db: Option<f64>` (serde default None, skipped when None). `track_from_encore` reads
`gain_db` from the Encore track object (Encore's volume normalisation, backlog item 3, will send a ReplayGain /
loudness offset per track in a later release; the engine side lands now). Semantics:

- Applied in the volume stage of the pipeline as an extra factor (dB added to `volume_db`), so it rides on the
  64-bit multiply that exists; the `volume` stage detail reads "−5.2 dB (track −7.2 dB · volume +2.0 dB)".
- A non-zero gain counts as "touching the samples": DSD pass-through is off for that track (`passthrough_target`'s
  `untouched` check includes it) and `bit_perfect` is false in the signal path.
- In bit-perfect mode (`dsp.bit_perfect`) the gain is ignored and the signal path says "track gain ignored (bit-
  perfect)".
- Clamp to −30 … +12 dB; out-of-range values are clamped and logged once per track.
- `cadenza-dsp`: if the volume stage lives in `cadenza_dsp::volume::Volume`, add the track gain as a second field
  or a separate stage rather than changing `Volume`'s meaning; Encore's server and phone build `cadenza-dsp` and use
  `Volume` as it is. Say in the report what changed in `cadenza-dsp`.
- Test: a WAV through the null output with `gain_db = -6.0206` comes out at half amplitude; with bit-perfect on,
  unchanged.

### 4.M `engine_description` without an Encore client; the embed API

`encore::state::engine_description(client, status, embedded)` needs a `Client` only for the host name. Change the
signature to `engine_description(status: &Status, host: &str, embedded: bool)` (the link passes
`client.device_name()` stripped of "Cadenza on "), and `heartbeat_state_as` likewise, so both build with no link.
Then `embed::EmbeddedPlayer` offers what the Iced app calls:

- `describe(&self) -> Value` – the `engine` object of section 3.2, `embedded: true`, host from `gethostname`.
- `state(&self) -> Value` – the whole heartbeat state (now playing, position, queue, signal, engine).
- `set(&self, patch: &serde_json::Map<String, Value>) -> Result<Vec<Adjustment>, String>` – `patch_settings` +
  `validate` (4.I); the `Err` is the reason the user sees; the result also lands in `engine.rejected` /
  `engine.adjustments` so a describe after a set shows the same thing.
- `outputs(&self) -> Vec<Value>` – the `[[id, label]]` list (`encore::state::outputs()`), and
  `devices(&self) -> Vec<DeviceInfo>` for a richer picker.
- `codecs(&self) -> Vec<&'static str>` – `supported_codecs()` (4.B).
- `test_sound(&self) -> Result<(), String>` – play one second of a −20 dBFS 1 kHz sine (generated, stereo, at the
  source rate 48 kHz) through the normal chain and the configured output, as a one-track queue with a marker id so
  no play is reported; an open failure returns the 4.G words. It must work while stopped and interrupt nothing when
  something is playing (refuse with "stop playback first" rather than cutting in).
- `play(&self, tracks: Vec<Track>, index, position)`, `control(&self, action: &str, value: Option<Value>) ->
  Result<(), String>` (reuse `api::control_command`), `status(&self) -> Arc<Status>`, `subscribe(&self) ->
  broadcast::Receiver<Event>` – thin wrappers over `Engine`, so the app never needs `engine()` directly.
- Keep `start`, `connect`, `disconnect`, `link`, `status_json`, `shutdown` unchanged for the Tauri app.
- Tests: `describe()` on a fresh player with the null output has every key of the table in section 3.2;
  `set({"dsd_rate":"dsd2048","dsd_packing":"dop"})` returns the DoP error as `Err` and `describe()["rejected"]` shows
  it; `test_sound()` on the null output finishes within 2 s and writes 48 000 frames.

### 4.N Position stuck at 0:00 (check and fix what applies)

Reproduce with the null output in real-time mode (`EngineOptions { realtime: true }`) and the Encore desktop
settings (long filter, WASAPI) in mind. Candidates:

1. The Opus failure (4.A): every track errors in `pump` and `advance()` moves on; the position never leaves 0.
   Fixed by 4.A and 4.C, and 4.E makes a failing chain stop visibly.
2. `Worker::position()` subtracts `chain.latency_seconds()` and the output's queued frames and clamps at 0. A
   16M-tap `sinc-xtr` filter at 44.1 → 705.6 kHz has a latency of several seconds, so the position reads 0:00 for
   that long after start and after every seek, while Encore's heartbeat shows exactly that. Publish
   `engine.latency_seconds` (section 3.2) so the UI can say "starting (filter latency 11 s)", and check that
   `latency_seconds` is right for minimum-phase filters (it should be near 0 there).
3. The null fallback (4.E) with `realtime` pacing: position advanced but silently; with 4.E it stops with an error.
4. WASAPI `write()` blocking on `wait_for_event(2000)` and returning `EventTimeout` every period when the stream
   never started (device in use after `initialize_client` passed): the worker logs an error per period and keeps
   pumping, the decoder position advances but nothing plays; with 4.G.3 this stops with the words.
5. Make sure `Status.position` is published at least every 500 ms while playing (`last_publish` / `dirty` logic in
   `run`) and that the heartbeat (2 s) carries the latest status, not a stale `Arc`.

Write down in the report which of these were real on the null output and which need the hardware.
