# Speed baseline before the 0.26 speed pass

The `perf_bench` table (server/src/perf_bench.rs) run on the tree as it was before step 7 of 0.26: commit 0d0090b
(batch A landed; the server is the 0.25.3 WIP's speed work, unmeasured until now). The after-numbers are in
[0.26.md](0.26.md).

How it was run:

    cd server && cargo test --release perf_bench -- --ignored --nocapture

The bench builds a synthetic library of 60 000 songs on 6 000 albums by 2 500 artists, 20 000 plays, 600 requests, 30
playlists of 50 songs and a Liked Songs list of 2 400 songs, then calls every endpoint the apps use while their pages
load. "cold" is one call against a fresh server (empty in-memory caches) on a copy of the database file; "warm" is
25 timed calls on one server after three untimed ones, p50 and p95. The last two rows load the home page's six calls at
once, the second time while a background thread reads the whole songs table and writes a row in a loop. MusicBrainz is
a local mock; translations are off for the bench account (the default; `BENCH_TRANSLATE=1` turns them on).

Machine: 4 vCPUs (Intel Xeon 2.10 GHz), 16 GB, Linux 6.18, local ext4 disk, no other load. rustc 1.97, SQLite
(bundled, libsqlite3-sys 0.35). The whole run took 2 min 33 s. Numbers from a different machine are not comparable
with these; compare the two tables in this folder with each other.

What the table says about the tree before the pass:

- Most cold numbers between 700 and 1000 ms are one cost: the first request after start builds the in-memory artist
  index from every song (about 700 ms for 60k songs), and anything that touches the index pays it once. `/api/system/status`
  (1.5 s cold, 300 ms warm) waits on a live MusicBrainz probe, the mock here; `new-releases` cold (3.3 s) builds its
  list from the catalog once and then keeps it for a week.
- Warm, the album and song lists are cheap already (the WIP's list cache); the song pages still run one sorted query per
  page before they are cached, which is what the pass changes. `albums q=echo` (133 ms) ranks 6 000 albums in memory on
  every call; `Liked Songs detail` (103 ms, 1.4 MB) is mostly the two body-rewriting middlewares parsing and writing the
  answer again. Both are the structural work of 0.29, not this pass.
- The home page under a background job (p95 60 ms against 30 ms) shows the readers helping: the writes of the background
  job do not stall the reads.
