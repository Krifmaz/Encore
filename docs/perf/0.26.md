# Speed pass of 0.26: before and after

The `perf_bench` table after step 7 of 0.26, next to the baseline from [0.26-baseline.md](0.26-baseline.md) (commit 0d0090b).
Same machine, same command, same synthetic library (60 000 songs, 6 000 albums, 2 500 artists):

    cd server && cargo test --release perf_bench -- --ignored --nocapture

Machine: 4 vCPUs (Intel Xeon 2.10 GHz), 16 GB, Linux 6.18, local ext4 disk, release build, translations off for the bench
account. Each cell reads `before → after`; "same" means the difference is under 5 percent or under 0.15 ms, which is
inside the run-to-run noise of this bench (two runs of the same code differ by that much; cold numbers differ by up to a
third, because a cold call pays for whatever background work the fresh server started).

## What changed in the server

- The songs list sorts the ids once per sort and keeps them until the songs change; every page is a slice of that list
  and fetches its 200 rows by id. The 0.25.3 WIP cached each page on its own, so the first visit to every page was
  another pass over the table (a sorted walk where a `lower(…)` index covered the sort, a full 60k-row sort for the
  added, released and duration sorts).
- Shuffle picks random ids from the same cached list instead of `ORDER BY RANDOM()` over every song.
- `library_version` (what drops the list caches and the artist index) moves only for statements that write `tracks`
  or `artist_alias`, matched by the table the statement names, not by the substring "tracks" anywhere in the SQL.
- Six indexes: `tracks(lower(artist))`, `requests(kind, lower(artist), lower(title))`, `requests(user_id)`,
  `playlist_items(track_id)`, `plays(track_id)`, `plays(played_at)`. Schema 26, so the usual backup is taken before the
  upgrade (the WIP's nine indexes came without a bump); `ANALYZE` right after the migration, `PRAGMA optimize` after
  every scan, a 128-statement cache per connection (rusqlite's default of 16 thrashed), `journal_size_limit` 64 MB.
- The translate layer does nothing while no account has translations on (one cached check, refreshed only after a
  write to the accounts), and when one has, it takes the user from the handler's own extractor instead of running the
  session and user queries a second time.
- The cover thumbnail pass runs after a scan only when the scan changed something (it used to walk every album's folder
  after the hourly scan).
- `ENCORE_DB_READERS` is documented (README, docker-compose.yml); the read connections stay off by themselves when the
  config folder is on a network file system (NFS, SMB/CIFS, FUSE – statfs magic), with a log line saying so.
- Settings → Diagnostics has a Server block: CPUs, memory (the container's limit when there is one), the file systems of
  /config and /music, the database size, whether anyone has translations on, the read connections in effect.

## Reading it

- Warm, the pages the owner opens most are a little faster or the same: `/api/requests` 19.9 → 10.5 ms (the request
  indexes and no second user lookup), `/api/stats/me` 24.9 → 19.7, the leaderboard 4.0 → 2.8, Liked Songs 103 → 97 ms,
  every small call about 0.1–0.5 ms less (the translate layer out of the way). The album and artist lists were already
  served from the WIP's list cache and stay where they were.
- The repeated song page (`tracks sort=…`) stays within noise: before, a page visited twice came straight from its own
  cache entry; now it fetches its 200 rows by id each time (about 1–2 ms), and the first visit to a page no longer sorts
  the table. The last two rows of the table measure that first-visit case directly: ten pages nobody had opened, one
  after the other, through the API; and, as a reference, what the old per-page sorted query costs on the database alone
  (cheap where the WIP's `lower(title)` index covers the sort, which is why the id list is a wash for the title, album
  and artist sorts and a clear win for added, released and duration). Most of the per-page time through the API is the
  answer path shared by both versions: cover lookups for albums seen for the first time, the two body-rewriting layers,
  gzip of 94 KiB.
- Cold numbers are not what the pass was about: between 700 and 1 100 ms they are one cost, the artist index built from
  every song on the first request after start (and `new-releases` 3 s builds its list from the catalog once a week).
  `albums q=echo` (140 ms) ranks 6 000 albums in memory per call and `Liked Songs detail` (1.4 MB) is mostly the two
  layers parsing and writing the body again; both are the structural work planned for 0.29 (the DB off the runtime
  threads, one enrichment pass instead of two middlewares, typed rows).
- Under a background job that reads the whole table and writes a row in a loop, the home page's p95 stays around 60 ms
  against 30 ms when idle, in both runs: the read connections do their job, the write connection's queue is what remains.

## What the owner can report

The Server block in Settings → Diagnostics (and its Copy report) answers the open question of the plan: CPUs, memory
limit, whether /config and /music are local or network, database size, translations on or off, read connections in
effect. With those, the two tables here say which numbers to expect on that box.
