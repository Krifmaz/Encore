# Speed of 0.29: the server in crates

The speed table of 0.29 next to the numbers of 0.26 ([0.26.md](0.26.md), after the 0.26 speed pass) and of 0.28 (the
tree right before this release's work, commit 2dbb361). Same command and same synthetic library for all three; 0.28 and
0.29 were measured on Oct 19, 2026 on the same machine, one run after the other, so the change between them is the work
of this release. The 0.26 column comes from another machine (see "Machine" below).

## How it is run

    cd server && cargo bench --bench perf

Since 0.29 the bench is `server/benches/perf.rs`, a plain program (no test harness) run by `cargo bench`. Up to 0.28
the same code was a test, `server/src/perf_bench.rs`, run with `cargo test --release perf_bench -- --ignored
--nocapture`; the 0.26 and 0.28 columns come from that command. Both build with the release profile of
`server/Cargo.toml` (`cargo bench` uses the bench profile, which takes its settings from it), so the bench measures the
code the release binary runs. `BENCH_COLD=main` times only the main pages cold; `BENCH_TRANSLATE=1` turns translations
on for the bench account.

The bench fills a synthetic library of 60 000 songs on 6 000 albums by 2 500 artists, 20 000 plays, 600 requests, 30
playlists of 50 songs and a Liked Songs list of 2 400 songs, then calls every endpoint the apps use while their pages
load. "cold" is one call against a fresh server (empty in-memory caches) on a copy of the database file; "warm" is 25
timed calls on one server after three untimed ones, p50 and p95. The bold rows load the home page's six calls at once,
the second time while a background thread reads the whole songs table and writes a row in a loop, then page through the
songs list. MusicBrainz is a local mock; translations are off for the bench account. Progress goes to stderr, the
table to stdout.

Machine: 4 vCPUs (Intel Xeon, reported as 2.80 GHz), 15 GB, Linux 6.18.44, a virtual disk, rustc 1.97.0. Nothing else
was building on it as far as we could see, but the load average and the CPU steal time were not recorded. 0.28 is built
with its own release profile (lto thin, codegen-units 4), 0.29 with its new one (fat LTO, one codegen unit). The two
versions ran interleaved: 0.29, 0.28, 0.29, 0.28, 0.29. The 0.28 numbers are the mean of its two runs, the 0.29 numbers
the median of its three. That is not the same statistic: the median leaves out 0.29's worst run while the mean keeps
0.28's, which favours 0.29 a little. The next table should use the median of three runs for both.

**Do not compare this table with the measurement of Oct 18** (the same 0.28 tree on another host, run before this
release's work: artists sort=name 19.1 ms, songs lists 6 to 8 ms, Liked Songs 60 ms, the leaderboard 2.3 ms, the
requests list 7.7 ms, home page in parallel 16.9 ms warm). Every warm number of 0.29 here is higher than those, but so is
every number of 0.28 here: today's 0.28 took 2.2 to 3.5 times the Oct 18 times (stats/me 2.15x, artists 2.54x, songs
2.74x, Liked Songs 2.95x, leaderboard 3.39x, requests 3.53x; about 2.7x in the middle), on a CPU reported as faster
(2.80 GHz against 2.10 GHz). A slower CPU would not explain that; other work on the same physical host during these runs
more likely does, and since the factor differs from row to row, no single factor converts one host's numbers into the
other's. So: compare 0.28 with 0.29 only within this table, and 0.26 only with numbers from its own host.

Each cell reads `0.26 · 0.28 → 0.29`, and the change in brackets is 0.29 against 0.28 (the work of this release).
"same" means the difference is under 5 percent or under 0.15 ms, inside the run-to-run noise of this bench (two runs
of the same code differ by that much warm; cold numbers differ by up to a third, because a cold call pays for whatever
background work the fresh server started). KiB is the size of the answer, 0.28 → 0.29; the answers are meant to be
byte for byte the same, so a different size is worth a look.

CI runs the same bench: the x86_64 build of a release (release.yml, job `server`) puts its table into the job summary,
and so does the Linux build of test-and-build (docker.yml, job `package`) when that workflow is started by hand (not on
every pull request: the bench's own fat-LTO build costs about a quarter of an hour of runner time). Those numbers come
from a GitHub runner, another machine with other neighbours: compare them only with other CI runs, not with this page.

## What changed in the server

- The server is a Cargo workspace of crates (`server/crates/*`) around a small `encore` binary; that alone changes no
  speed. The runtime state that used to sit in process-wide statics (caches, slots, the artist index) belongs to each
  server's state now.
- The database calls of the busy handlers (home, library lists, album, artist, playlist, search, For you, the requests
  list) run on the blocking thread pool, reads on the read connections and writes on the one write connection, instead
  of on the threads that serve requests.
- One enrichment pass inside those handlers (`cover_v`, `cover_color`, `artists`, the translations) instead of two
  layers that parsed every JSON answer and wrote it again.
- One query per batch of up to 500 ids where a loop asked once per album or song (Discover, an artist's catalogue, For
  you, search, the alias refresh, deleting songs); the scan writes 200 files per transaction with one library version
  bump per batch, and after a scan or an import the cover pass looks only at the albums that changed.
- Album search ranks the matches in memory over the cached albums list instead of a 30,000-value `IN` list.
- The library lists, the outside-service answers and the MusicBrainz answers are kept in caches bounded by bytes and by
  entries (least recently used out first); the leaderboard ranking is kept until a request, play, like, playlist or
  account is written (60 s at most).
- Nothing slow on the request path: disk usage and the download-folder sizes (Storage), the tool versions
  (Diagnostics) and the Soulseek status line come from background refreshers; requests slower than 250 ms are logged,
  and `GET /api/admin/perf` lists the last 500 slow ones with p50 and p95 per route, the cache sizes and the waits for a
  database connection.
- The release profile: fat LTO and one codegen unit.

### After the table was measured

The review of this page found work still done on the threads that serve requests, and slow answers the table does not
show. These changes came after the table above, so it does not reflect them; the next measurement will.

- Home's own numbers (`/api/stats/me`) and the leaderboard run on the blocking pool; your plays, time listened, top
  artist and requests are kept until a request, play, like or playlist is written, like the ranking.
- `/api/library/storage` (the side bar's meter, at every start of the web app) and `/api/library/stats` (polled by the
  Library page) read their totals on a read connection once per state of the library; the disk and folder sizes no
  longer wait after every library change (the last numbers are shown while new ones are worked out). The bench now
  calls `/api/library/storage` too.
- The request worker, the playlist import preview, adding songs to a playlist, the rematch and the sync use one kept
  index of the library's songs (built on the blocking pool, again only after the songs changed, dropped after five idle
  minutes) instead of reading the whole songs table for each song request; a rematch writes its changes in one
  transaction.
- At start the server makes the artist index, the download tools' versions and Home's new releases in the background,
  so the first pages after a restart don't wait for them; callers that arrive while one is being made wait for that
  one instead of starting their own.
- The artist alias refresh saves 50 artists per transaction, so the library version (and with it the cached lists and
  the artist index) moves once a minute during the alias pass instead of about once a second.
- Smaller ones: passwords are hashed and checked on the blocking pool; unliking a song renumbers Liked Songs in one
  transaction; the batched request look-up uses both columns of its index; the requests list maps its rows in the same
  blocking hop as the query; For you, the genres, the artist page's popular songs, the artist catalogue, the playlists
  list, likes, share links and artwork embedding no longer query on the async threads (and several of them ask once
  instead of once per item); the Soulseek share lists are held to 32 MB and 20 users and show in `/api/admin/perf`; a
  made-up HTTP method no longer adds a row to `/api/admin/perf`.

## Reading it

- **Warm, every list got faster.** The albums lists take about half the time (6 to 8 ms → 3 to 4 ms), the artists
  lists and the songs lists about 40 percent less, Liked Songs 177 → 104 ms, the requests list 27 → 12 ms. The likely
  main cause is the enrichment pass: 0.28 parsed each JSON answer that named an album again after the handler wrote it
  (the bigger the answer, the more that cost); 0.29 adds covers and artist links to the value before it is written
  once.
- **Album search** (`albums q=echo`): 204 → 32 ms warm, the ranking in memory instead of the long `IN` list.
- **Leaderboard**: 7.8 → 0.3 ms warm, the ranking is kept until something it counts is written; the home page's six
  calls in parallel take 23 ms instead of 42, and the songs list paged by a new listener 164 ms instead of 309.
- **Cold**: mostly 10 to 30 percent less, inside or near the noise of a cold call. The exception is
  `/api/system/tools`, 2 → 495 ms: up to 0.28 the tool versions (`yt-dlp --version` and the others) were kept in a
  process-wide cache, which the bench's "fresh" servers in one process shared, so 0.28's cold call never ran them.
  Since 0.29 each server has its own, and a fresh server's first call runs the version probes once (as the first call
  after a start always did in production). After that the versions come from the cache and a background refresh.
- **Inside the noise**: the cold home-page calls (requests, new releases, library stats), the index side bars, and the
  sub-millisecond rows, where a p95 that moves by a few tenths of a millisecond shows as a large percentage.
- **Outside the noise and not explained**: `albums sort=added` cold 149 → 209 ms (+40 percent), more than the cold
  noise of about a third; the other album sorts got faster cold. The list is built by the same query as the other sorts
  with another `ORDER BY`, so the likely cause is what the fresh server was doing in the background at that moment
  (the cover pass of a cold server starts at once), but that was not checked.
- **Slower**: `/api/library/search q=echo mirror song` warm p50 50.5 → 55.7 ms (+10 percent; p95 the same). Every 0.29
  run was above every 0.28 run (52.8 to 59.7 against 49.9 and 51.2), so it is probably real. The search code itself is
  the same as 0.28's apart from module paths and the state type it takes, and the enrichment does nothing for this
  answer, so the likely cause is the new release profile (fat LTO and one codegen unit inline and lay out code
  differently), which this table does not measure on its own. To settle it, run the bench once on 0.29 built with
  `CARGO_PROFILE_RELEASE_LTO=thin CARGO_PROFILE_RELEASE_CODEGEN_UNITS=4` next to the fat build on the same host, and keep
  fat LTO only if it wins overall.
- **The background job row** (home page while a thread reads the whole songs table): p50 49 → 30 ms, p95 about the
  same; the handlers' database work no longer runs on the threads that serve requests.
- The request worker built its in-memory index of the whole library for every song request it started, on the server's
  async threads (0.28 did the same; on a 60 000-song library a queue of requests kept all four threads busy for
  minutes). That is fixed since the table was measured (see "After the table was measured"); the bench does not run
  the worker, so neither the problem nor the fix shows here.
