## Encore 0.29.0

This release is mostly inside the server: it is now built from separate parts, code nothing used is gone, and the busiest pages do less work per request. Pages, buttons, settings and the API stay as they were, apart from what is listed under *Storage problems*, *When the audio check is wrong*, *The picker keeps searches*, *Torrents and Usenet*, *Apps & sources is now four pages*, *Removed*, *Soulseek* and *For API users and developers* below. If something you use behaves differently from 0.28, that is a bug; please report it.

### Storage problems no longer cost you downloads
From Oct 17 to 19 the owner's server failed Deezer downloads with "All sources exhausted (streamrip: Input/output error (os error 5))": *Illuminate EP* reached 17 attempts, and *C U Next Tuesday* was downloaded but never imported. streamrip worked; a damaged folder on one disk of the mergerfs pool behind `/music` failed whenever an album was moved there. Encore said nothing useful: an error without a step or a path, nothing in `docker logs`, the failure counted against the source, every other source tried, the downloaded files deleted, and the request started again from scratch. Now:
- **Errors name the step, the operation, the path and the error.** Instead of "streamrip: Input/output error (os error 5)" a request says "import failed: mkdir /music/Duumu/Illuminate EP: Input/output error (os error 5) – storage problem, not the source". Every file step and program start of every source and of the import does this: streamrip, yt-dlp, links, Soulseek, torrents and Usenet, the staging folder, the move into the library, tags and covers. The end of the sentence says what kind of problem it is: "storage problem, not the source" (an I/O error, a read-only or full disk, a used-up quota, a network share that went away: EIO, EROFS, ENOSPC, EDQUOT, ENOTCONN, ESTALE, EHOSTDOWN), "Encore may not write there (check the folder's owner, PUID/PGID)", "the folder is missing (check the volume mapping)", "the program is missing" or "Encore may not run it (check the file's mode and owner, or a noexec mount)". Messages are no longer cut at 300 characters.
- **A storage problem is not a problem of the source.** When writing to the library, the staging folder or a download client's folder fails that way, the source is not counted as failed, no other source is tried, no attempt is counted and the downloaded files stay where they are. The request shows **Waiting** – "Waiting: library storage error – import failed: mkdir /music/…: Input/output error (os error 5). Next try at 14:20" – and only the import is tried again: every 10 minutes, at once when the storage check passes, when an admin presses *Check again*, or when someone presses *Import again*. When the staging folder fails before anything was downloaded, the request waits the same way ("Waiting: storage error – staging failed: …") and the download step runs again once the folder can be written, still without counting an attempt. The Oct 17 "Read-only file system (os error 30)" from yt-dlp now waits like this too, instead of failing every request.
- **A check before every import.** Encore makes a folder `.encore-probe-<pid>-<n>`, writes 4 KiB into it and flushes them to the disk, and removes both again: in the library, in the album's folder as far as it exists (with mergerfs the library's top folder can be fine while the disk holding the artist's folder is not) and in the staging folder, each at most once a minute; a waiting request's own folder is checked exactly each time it is tried again. When that check hits a storage problem, imports pause: every request that reaches its import waits, and the Requests page and the Downloader page show a banner. Admins see "Imports are paused: /music is not writable – mkdir /music/.encore-probe-…: Input/output error (os error 5). Checked 14:10, next check 14:20" with *Check again*; everyone else sees "Imports are paused because of a storage problem on the server. Your downloads are kept and will be added when it is fixed." A permission problem ("Permission denied") does not pause anything: the import itself fails then, with what to check. The check runs again every 10 minutes and when an admin presses *Check again*; once it passes, the waiting imports go on at once. A disk can fail on a write the check can't see (a full disk, a bad spot): then each waiting import is still tried every 10 minutes, but a check that passes before another import doesn't wake them all, so they are not tried over and over. The pause ends by itself once no request waits for that folder any more (cancelled, deleted or imported). The pause survives a restart. The checks run one at a time and outside the request queue's own loop, so a network share that hangs holds up only the imports.
- **Finished downloads are kept.** An import into the library is all or nothing: each file is linked or copied next to its place as `<name>.encore-part` and written to the disk, then all of them are renamed into place, and only then are the downloaded copies removed. A failure part way removes the part files and leaves every download where it was, and the banner names the library's folder that failed, not the download folder. A staging folder that holds a finished download (`staging/request-<id>`) is removed only after a successful import, or when someone cancels or deletes the request; files in Soulseek's, the torrent client's or the Usenet client's folders are not removed for a storage problem, and cancelling a request whose files are kept no longer removes its torrent or cancels its Soulseek transfer. Kept files that can't be looked at (a network share or FUSE mount that went away, a disk error) are not taken for gone: the request keeps waiting with them instead of downloading again. Files that can't be read are a storage problem too, never "the wrong audio". A disk error that streamrip itself reports while it writes into the staging folder ("[Errno 5] Input/output error: '…'") waits the same way instead of trying the next source. Picking another download for a request whose files wait to be imported is refused ("This request has downloaded files waiting to be imported – Import again or cancel it first"), and *Cancel* and *Remove from list* on such a request ask first ("Its downloaded files have not been imported yet and can't be imported after this."). *Remove artist* now also cancels the artist's waiting requests, so a waiting import can't bring the artist back. The daily clean-up leaves the staging folders of waiting requests, and of requests with kept files, alone.
- **Import again.** A request with kept files shows *Import again* where *Retry* was ("Import the downloaded files again – nothing is downloaded again"), and *Retry* on such a request does the same. An import that fails for another reason, a permission say, fails with its files kept ("import failed: mkdir /music/Band/Album: Permission denied (os error 13) – Encore may not write there (check the folder's owner, PUID/PGID)"), without trying another source; *Import again* imports them once it is fixed. A link of which only some files could be imported keeps the others for *Import again* instead of deleting them ("Downloaded 1 of 2 file(s) – the rest could not be imported: …"). *Retry* on a playlist imports the songs whose files are kept the same way. On such a row the admin's ⋯ menu says *Delete downloaded files*.
- **Picked up at start.** When the server starts, an import that was running goes back to waiting (whatever its source), and a failed request whose downloaded files are still in its staging folder (from an older version too) waits to be imported. That rescues downloads like *C U Next Tuesday*, if their files are still there.
- **Attempts count only answers from a source.** *Attempts* counts the runs that ended failed or completed at a source. Waiting for the storage or for Soulseek, a paused import, *Import again*, the 10-minute retry, the rescue at start, a cancelled run, a run a pick took over and an import that failed with its files kept never count.
- **One Waiting status.** The *Waiting* badge (amber, no spinner) is also used for requests waiting for Soulseek (see *Soulseek* below; same words as before, "Waiting for Soulseek – next attempt at 14:20"). *Active* lists waiting requests, and they can be cancelled.
- **The log says it.** Every source failure and every change of the storage writes one line to the activity log and to the server's own output (`docker logs`), with the request, the step, the operation, the path and the error: "storage: /music not writable – mkdir …; imports paused", "storage: /music writable again; 3 imports resumed", "Request #12 (Duumu – Illuminate EP) waits for the storage: import failed: …", "Request #12 (Duumu – Illuminate EP): streamrip: …".
- **streamrip runs without a terminal**, for downloads and for its config checks: no input, a session of its own with no terminal (a prompt or a write to `/dev/tty` can't hang or fail a run), progress bars off, `TERM=dumb`, `NO_COLOR=1`, its home in Encore's data folder. At the time limit, or when the request is cancelled, the whole run stops, ffmpeg included. Its update check is off from streamrip 2.4.10, which the image now installs (2.4.9 has no switch for it: it asks GitHub before every run, for at most 10 seconds, and never fails because of it). A start that fails names the program ("download failed: start /config/tools/venv/bin/rip: …"); streamrip's config is written whole or not at all, keeps its permissions, and a config that can't be read is never written back empty.
- **streamrip's output is kept** with the request on every outcome, success or failure (up to 20,000 characters, its start and its end), in its details (once: the log says where it is), and a failed request keeps streamrip's own words. The *Test* and *Reset streamrip config* buttons in Settings → Downloads → Qobuz / Tidal / Deezer (streamrip) show their whole error too.
- **Readable errors with Copy.** A click on a request's line, or ⋯ → *Details*, opens its whole text with *Copy*: title, artist, status and what it waits for, the message, the next try, attempts, source, the error with its step, operation, path and errno, where the downloaded files are kept, every log line, streamrip's output, who asked for it and when, the request id and the server version – ready to paste into a bug report. Members see their own requests without the server's folders: a wait for the storage reads "Waiting: a storage problem on the server – your download is kept and will be added when it is fixed. Next try at 14:20", as their banner does. The picker's errors per source, the Activity log lines and transfer errors, the Soulseek page, Diagnostics (app crashes, checks), the settings' *Test* results and the connection badges open in full or have *Copy* too. Error messages show their whole text with *Copy*; on the website and in the desktop app they stay until they are closed. *Copy* also works on a server reached over plain `http://`.
- **Fixes**: the picker's Tidal search answered "Tidal API 400 INVALID_RESOURCE_ID" for every search: Tidal moved its search, and Encore uses the new one (an empty search asks nothing); a Tidal error in the automatic Tidal match is now reported instead of read as "not on Tidal". Ke$ha, A$AP Rocky, P!nk and names like them now match releases that spell them with letters (Kesha, ASAP, Pink), and indexers and Soulseek are asked for "Kesha Cannibal" instead of "Ke ha Cannibal". A link whose download could not be imported fails with the reason ("Downloaded, but nothing could be imported: …") instead of "Downloaded 0 file(s)" shown as Available, a song you already have says "Already in your library", and a link's own title and artist are shown on the request instead of the link. The setting *Staging path for yt-dlp downloads* is now *Staging folder for downloads* ("Where downloads (streamrip, yt-dlp, links) are saved before they are tagged and moved into the library").

### When the audio check is wrong: Keep anyway and Download anyway
On Oct 19 the owner's request for "Moonlight Shadow (nightcore)" by Machine Time failed after 10 attempts with "All sources exhausted (ytdlp: YouTube match was the wrong audio (audio is "diase – …"". The fingerprint check (AcoustID) turned every download away and deleted it, and the only way around it was the global switch *Reject downloads whose audio is a different song/version (and try the next source)*, for everything. Now:
- **A download the audio check turns away is kept.** Its files move to `<staging folder>/rejected-<request id>/<n>/` instead of being deleted, from every source: yt-dlp, streamrip, Soulseek (out of slskd's folder) and torrents and Usenet (out of the client's folder, before the torrent is removed). The request remembers the newest three; an older one's files go. Only the audio check's rejections are kept: the quality check and the wrong-release check work as before. Kept files go when the request completes or is deleted, and an hourly look removes those older than 7 days and those of requests that were cancelled, denied or cleared from the list.
- **The reason is shown in full**: "The audio sounds like Diase – Sun, not Moonlight Shadow", on its own line under the request (wrapped, never cut) and at the top of its details. *Copy* adds "Turned away by the audio check (oldest first):" with, for each download, where it came from, the check's own words, when, and whether its files are still kept.
- **Keep anyway** imports the kept file without the check. The song is then marked as confirmed by that person ("✓ confirmed", "Confirmed by alice"), the same as the library's *This is the right song*, so the verification task never flags it again. The request reads "Waiting to import the kept download", then "Downloaded from Deezer via streamrip – kept anyway by alice". Only the audio check is off: the quality check (fake lossless, upsampled, the wrong length) and the wrong-release check still apply, and a kept download they turn away ends the request with that reason ("Kept anyway, but the quality check turned it away: …"); it is then no longer offered.
- **Download anyway** is offered instead when the kept file is gone: it asks the same source for the same link again, without the audio check for that one download ("Downloading it again without the audio check", then "… – downloaded anyway by alice, without the audio check"). The check is on again for the request's next download.
- **Who sees the buttons**: admins, and members with the permission *Fix their own downloads* on their own requests, the same people as for *Retry*. Others see the reason without a button. The website and the desktop app now also hide *Retry* and *Retry failed* from members without that permission, and the phone app its *Retry failed* (it already hid *Retry*); the server refused them anyway. The buttons show on failed requests and on requests that moved on to another source and are still looking; not on completed, pending or cancelled ones, not during a storage wait and not while *Import again* is offered.
- **Automatic downloads** still move on to the next result or source when the check turns one away. **A download you picked by hand** that the check turns away fails at once with the reason and offers *Keep anyway* (a pick never falls through to other sources).
- **The picker's "Don't check the audio"** switch, beside *Lossless only* (off by default, remembered on each device): a pick made with it on is imported even when the check says it is another song, still tagged with MusicBrainz data, de-duplicated and checked for quality and the right release, and its songs are confirmed by the person who picked ("… – picked by alice without the audio check"). Only admins and members with *Fix their own downloads* see it; the server refuses it from others ("Ask an admin to pick without the audio check").
- **Versions the fingerprint can't judge are no longer fingerprinted.** A nightcore, sped up, slowed, slowed + reverb, 8D, bass boosted, daycore or chipmunk copy is re-pitched or re-timed audio, which AcoustID knows as the original or as something unrelated. Titles with these words (and the other words Encore already reads as such a version: reverb, chopped, lo-fi, pitched, TikTok version) are checked by length and title only, on import and in the verification task, and the request's log says so. The words count in brackets or after " - " ("Song (Slowed)", "Song - Sped Up"); at the bare end of a title only nightcore, sped up, daycore, 8D, slowed + reverb and bass boosted do, so songs called "Slowed" or "Fade Into Reverb" are still fingerprinted. The log line: "Nightcore version – the fingerprint can't judge re-pitched audio; checked by length and title only". "Chipmunk" is new in that list, so a chipmunk copy is now also skipped as an unwanted version when the request didn't ask for one, as nightcore already was.
- The website, the desktop app and the phone app all have the buttons, the reason and the switch, with the same words: on the request rows (Requests, Home's downloads in progress, and the Downloader page on the website and the desktop app) and in the request's details.

### The picker keeps searches
Every picker opened for a Soulseek album started a new Soulseek search, also right after the request's own search had found the same files. Now:
- **Soulseek and Torrents & Usenet answers are kept on the server** for a day (an answer with no results for an hour): the picker's searches, the requests' own Soulseek and indexer searches, and the Soulseek page's. Opening the picker again shows them at once, with "Found at 14:02 · Search again" (or "Found yesterday at 22:10"); when the words differ from the search box it says which ones (`for "Illuminate EP"`). Nothing is searched.
- **Search again** searches that one source now, through the Soulseek search gate (one search at a time, 3 seconds apart); the kept results stay on screen until the new answer comes.
- **While Soulseek isn't connected**, kept results still show and can be picked: the download waits for Soulseek. Instead of *Search again* the line says why ("Soulseek isn't connected – next attempt at 14:20").
- The picker's Soulseek text is now the same as the request's own ("Mike Oldfield Moonlight Shadow", brackets left out), so it finds what the request already searched for. Two pickers asking for the same words make one search, and a search goes on (and is kept) when its picker is closed.
- The kept answers are in their own file, `<config folder>/cache/search-cache.db` (at most 32 MB, oldest first out). It can be deleted at any time; restoring a database backup deletes it. A damaged file is set aside and started again; while it can't be opened, searches run as before.
- The website, the desktop app and the phone app show the line and *Search again*. **Reload an open website tab once after updating the server**: an older page reads the picker's new answer as "No results.".

### Torrents and Usenet
The owner reported "i feel like the usenet and torrent isnt working". The causes found (`wf/torrents-diagnosis.md`) are fixed:
- **Order**: with *Highest quality first* (the default), a request tries Qobuz/Tidal/Deezer, then FLAC on Soulseek, then torrents and Usenet, then Soulseek in any format, then YouTube Music, wherever `torznab` stands in *Source order*. Before, Soulseek MP3s came before the indexers. Requests for a lossless copy (upgrades) search the indexers too and take only lossless releases. Automatic song requests still skip the indexers (the setting says *Albums only*); the picker covers songs.
- **Encore fetches the release itself** from Prowlarr and hands qBittorrent the magnet or the `.torrent` file, and SABnzbd and NZBGet the `.nzb`, instead of Prowlarr's link, which a client behind a VPN or on another network often couldn't open. When Encore can't fetch it, it hands over the link as before. qBittorrent downloads are followed by their info hash, and a new torrent gets two minutes to show up in qBittorrent instead of being dropped at the first look.
- **A download client that doesn't answer for a while no longer loses the download**: the request says "qBittorrent not answering – asking again (…)" and keeps asking for as long as *Try the next release after a stall of (minutes)* allows; only then does it give up and remove the download. A qBittorrent that forgot the session is logged in again.
- **Queues**: a torrent or Usenet job waiting in its client's queue no longer counts as stalled ("qBittorrent: queued – its limit of downloads at once is reached"); new torrents are added at the top of the queue and started, and stopped torrents are started again. Transmission and Deluge too: new torrents are added started, a queued one waits without a stall, and one stopped or paused before it finished is started again. A job that stays queued for six stall times (12 hours with the default 120 minutes) is given up and the next release tried ("qBittorrent kept it queued for 12 hours"), and a paused SABnzbd queue (its own pause when the disk runs low, or a schedule) counts as a stall ("SABnzbd: its queue is paused"). A release qBittorrent is already downloading for another request (an album, and a song picked from it) is left to that request: "qBittorrent is already downloading this release for another request – pick another release", and the next release is tried. A torrent still moving its files isn't taken for finished, and torrents keep their own folder even when qBittorrent is set to create none.
- **Finding the right release**: titles with an edition ("Rodeo (Expanded Edition)") find releases named without it; "ACDC" counts for AC/DC; a self-titled album no longer takes another album of the artist (the release must name it twice or carry its year; "Led Zeppelin II" is another album unless the year matches); releases with extra words or another year rank lower. With a known track count the size limits follow it (2 MB per track, up to 4 GB or 400 MB per track), so singles and big hi-res sets are no longer dropped. The picker searches the indexers with the same clean names as the requests ("Travis Scott 3500", not "… (feat. Future & 2 Chainz)"). A CD image with a cue sheet ("[FLAC image+cue]") ranks below a release in tracks, even an MP3 one, since Encore doesn't split images. Song releases named in plain letters ("Beyonce", "Dont", "Kesha") rank as high as those with the accents or symbols.
- **Fewer searches at once**: the requests' own indexer searches run two at a time ("Waiting for other requests' indexer searches (two at a time)…"), so *Request discography* no longer sends every search at once; the album-only search runs only when "artist album" found nothing; the picker's searches don't wait. Prowlarr gets 2 minutes to answer, and a timeout says that one of its indexers is slow instead of "unreachable".
- **NZBGet** no longer turns later releases away as duplicates; **SABnzbd** jobs moved to its archive are found there.
- **Clearer failures**: a finished download in a folder Encore can't see stays in the client and names the path Encore looked at ("mount the client's download folder in Encore's container at the same path"), and no other release is tried. A client's path in a category folder or on Windows ("D:\Usenet\complete\music\encore-12") is found under the download folder Encore sees. A finished download Encore may not read (the client writes its files as another user) stays in the client and says what to check (PUID/PGID); one the disk can't read waits for the storage, as in *Storage problems*. SABnzbd and NZBGet are asked to unpack Encore's downloads whatever their category says (SABnzbd: repair, unpack and delete the archives); a release still packed says so ("the release is still packed (RAR/ZIP/7z) – SABnzbd didn't unpack it"), and a packed torrent says that Encore doesn't unpack it. API keys no longer appear in error messages.
- **Prowlarr's API key stays on the server.** The picker's Torrents & Usenet rows used to carry Prowlarr's download links with its API key, which gives full access to Prowlarr and the indexer logins in it, to everyone who may pick downloads. The rows now carry the links sealed, and the server puts the key back only into a link it sealed when the pick is downloaded.
- **Another album of the artist is turned away by its tags.** When there is no track list to compare a download with (MusicBrainz didn't match it and the source gave none), only the artist was checked, so another album of the right artist was imported under its own tags. Now a download whose album tags all name another album ("Homework" for "Discovery", "Led Zeppelin II" for "Led Zeppelin") is turned away as the wrong release ("Wrong release: the download is the album “Homework”, not “Discovery”"), from every source, like one by another artist: an automatic download moves on to the next release, a hand pick fails with that reason. An edition, a year, a disc number or the artist's name in the tag still counts as the album, and tags in another script, "Unknown Album" or only the artist's name are not judged.
- **The container leaves the download clients' folders to them.** At start the image handed every folder the environment names to Encore's user (PUID/PGID), the download clients' too (`QBIT_DOWNLOAD_PATH`, `SAB_DOWNLOAD_PATH`, `NZBGET_DOWNLOAD_PATH`, `TRANSMISSION_DOWNLOAD_PATH`, `DELUGE_DOWNLOAD_PATH`, `RTORRENT_DOWNLOAD_PATH`), so a client running as another user could no longer write there. An existing client folder is now left as it is; only one the script creates is handed over. The staging, Soulseek and blackhole folders are handed over as before.
- **Test connection** counts only Prowlarr indexers with music (Audio) categories and fails when there are none; SABnzbd's *Test* needs the full API key (it passed with the NZB key before) and names a wrong or missing key and SABnzbd's host name check (`host_whitelist`); a Prowlarr address with spaces, a line break or a pasted feed path (`/api`, `/1/api`) is cut to its base. The rTorrent help names ruTorrent's `/plugins/rpc/rpc.php`.
- Not changed: torrents are still removed after the import (no seeding), FLAC+CUE images are not split, and Encore doesn't unpack archives.

### Apps & sources is now four pages
Settings → Server's *Apps & sources* held everything from Verification & duplicates to Roon. It is now four pages, in this order after General:
- **Library**: Library & tagging, Verification & duplicates.
- **Downloads**: the Download tools card, Download pipeline, Release types, Qobuz / Tidal / Deezer (streamrip), Torrents & Usenet, Soulseek, YouTube Music & links, YouTube sign-in, and "How requests are fulfilled".
- **Integrations**: Integrations (API keys), Media servers, Roon.
- **Server processing**: Server processing (Cadenza).

Old links keep working: `#/settings?s=apps` opens Downloads, `tagging` opens Library, `services` opens Integrations, and a card's own name (`?s=slskd`, `?s=verify`, `?s=cadenza`) opens the page that holds it. Messages, the README, docker-compose.yml and the YouTube browser extension name the new pages ("Settings → Downloads → Soulseek"). The website, the desktop app and the phone app show the same four pages.

### The classic desktop app is gone
*In this server-only release: 0.27 was not released on its own, so the classic app's last build is the one you have (0.26), and the new desktop app is not attached yet: it comes with the next app release. Keep the classic app until then; it keeps working with this server (see Older apps with this server).*
- **The classic desktop app (Tauri) is removed.** Its last build is 0.26.8's (0.27 was not released), under the file names `Encore-Setup-<version>.exe`, `Encore-<version>-mac.dmg`, `Encore-classic-<version>-linux-x86_64.AppImage`, `Encore-<version>-linux-amd64.deb` and `.rpm`. From this release on these files are no longer built, attached to a release or carried over from an older one, and its update file (`latest.json`) is no longer published: the classic app stays on the version it has and will not offer this release or any later one.
- **When the next app release is out**, do the following (until then keep the classic app; this release attaches no desktop app).
- **What to do instead: install the desktop app** that replaces it, from that release on the [Releases page](https://github.com/Krifmaz/Encore/releases): **Windows** `Encore-<version>-windows-x86_64.exe` (installs for your user, no administrator rights), **macOS** `Encore-<version>-macos-universal.dmg` (if macOS will not open it the first time: System Settings → Privacy & Security → Open Anyway), **Linux** `Encore-<version>-linux-x86_64.AppImage` or `encore_<version>_amd64.deb`. It is native (no web view), plays every song through Cadenza on the computer, and updates itself from then on (each download is checked against the release's `SHA256SUMS`).
- **Nothing is carried over from the classic app.** The first start asks for your server and your sign-in. Its Cadenza settings and the songs it saved for offline stay in its own folder; save the songs again with *Save for offline* on a song, an album or a playlist in the new app.
- **Then remove the classic app.** On Windows, run `uninstall.exe` in its folder (`%LOCALAPPDATA%\Encore` unless you chose another; `uninstall-encore-desktop.exe` there is the new app's, leave that one). On macOS the new `Encore.app` has already taken the old one's place in Applications. On Linux, delete its AppImage or remove its `.deb` or `.rpm` package. Its settings and saved songs may stay behind in folders named `app.encore.client` (under `~/.config` and `~/.local/share` on Linux, `~/Library/Application Support` on macOS, `%APPDATA%` on Windows); delete them by hand once you no longer need them.
- **In the browser nothing changes.** The web app had a few parts that only appeared inside the classic app: Settings → This computer, *Change server*, the mini player, the *Offline music* page, and signing Cadenza on this computer in to your server. They are gone from the web app's code; the new desktop app has its own of each. The website's *Download for offline* (0.28) is unchanged.

### Removed
- **The Lidarr and HiFi settings.** `hifi_enabled`, `hifi_api_url` and `hifi_quality` no longer appear in the server's settings (the HiFi source went in 2026.10.11.3); the seven `lidarr_*` settings (Lidarr went in 2026.10.11.1) were already hidden and are now gone from the code too. Values saved for them stay in the database and are not read; `HIFI_*` and `LIDARR_*` environment variables did nothing before and still do nothing, so they can go from your compose file.
- **Old names in the source order.** If *Source order* (Settings → Downloads → Download pipeline, or `ENCORE_SOURCE_ORDER`) still names `lidarr` or `hifi`, edit it yourself: take them out, and put `torznab` where `lidarr` stood if torrents and Usenet should be tried at that point. Encore does not change the saved order. Until 0.28 Encore read `lidarr` as `torznab` and left `hifi` out; now a request skips both names without a note in its log, and torrents/Usenet (`torznab`), when the order does not name them, are tried just before YouTube Music. For example, `lidarr,slskd,ytdlp` used to try torrents, then Soulseek, then YouTube Music; now it tries Soulseek, then torrents, then YouTube Music.
- **Six API routes no app called** (see *For API users and developers*).

### Less work per page
- The database work of the busiest pages (Home, the library lists, the album, artist and playlist pages, search, For you, Requests) runs on threads of its own, so one slow query no longer holds up the other requests the server is answering.
- Covers, artist links and translations are added to an answer in one pass inside the page's own code, instead of by two layers that read every answer back and wrote it again. The answers carry the same fields and values as before. One small difference: a few times with a fraction of a second (when a song was added, a file's date) are now sent exactly as stored, where 0.28 could round the last digit.
- Lists that looked up each album or song on its own (Discover, an artist's discography, For you, search) now ask once per batch. A library scan writes its songs in batches, and after a scan or an import only the albums that changed get their covers looked at again, instead of the whole library.
- The lists the server keeps in memory have a size limit, so a big library can't grow them without end.
- The slow checks no longer run while a page waits: disk space and folder sizes on the Storage page, the tool versions on the Diagnostics page and the Soulseek status line come from a copy the server refreshes in the background. They can be a little behind: disk space and folder sizes up to a minute (after a song is added or deleted, the next look still shows the numbers from before while new ones are worked out), the Soulseek status up to 5 seconds. The leaderboard's totals, your rank and your own numbers on Home are kept between calls and worked out again after a like, a playlist, a request or a play, so they are as current as before. The service checks on the Diagnostics page (MusicBrainz, the download clients and the others) stay live.
- The request queue no longer reads the whole library for every song it starts: it keeps one index of the library's songs and builds it again only after the songs changed. Importing a playlist, its preview, the rematch and the sync use the same index.
- Right after a start the server prepares, in the background, what the first pages would otherwise wait for: the list of artists, the versions of the download tools and Home's new releases.
- The numbers before and after, measured the same way as for 0.26, are in `docs/perf/0.29.md`.

### The server's settings pages come from the server
Settings → General, Library, Downloads, Email & notifications and the other server cards are now drawn from a description the server sends with every field's label, help line, type, choices and when it shows, instead of from a copy built into the web app; the phone app can draw the same cards later. They look and work as before. A label, help line, choice or field that differs from 0.28 is a bug.

### Soulseek: Encore reconnects on its own schedule and searches one at a time
On Oct 19 the owner's server showed "Disconnected – can't reach server.slsknet.org:2242: The wait timed out after 5000 milliseconds" while the network and the VPN were fine, after a bulk retry of hundreds of failed downloads had fired hundreds of searches (most of them refused: "Only one concurrent search", "must be connected and logged in"). The Soulseek server ignores logins from an address that knocks too often, and slskd, the Soulseek engine Encore runs, tried again within a second after every failure. Now:
- **Encore decides when to connect, and slskd can't knock by itself.** slskd 0.26 starts its own retry loop again at once after every session that drops (and after a connection attempt that is cancelled), and that can't be switched off. So slskd now reaches the Soulseek server only through Encore: on the normal connection slskd.yml names a relay of Encore's on `127.0.0.1` as the server, and through the VPN Encore's SOCKS proxy does the same job. Encore lets one connection through per attempt of its own (`PUT /api/v0/server`); slskd's own attempts are turned away on the machine itself in a few milliseconds and never reach the server. Once slskd waits between two of its own attempts, Encore quiets it (`DELETE /api/v0/server`). The attempts follow Encore's schedule: 30 seconds, 1, 2, 5 and 10 minutes, then every 15 minutes, each up to 20 % earlier or later, never two attempts within 30 seconds, one at a time. A session that stayed logged in for 10 minutes starts the schedule over. The schedule is kept in `slskd/encore-session.json` in the config folder, so restarting Encore doesn't log in at once either.
- **A restart of slskd is not a failure.** When Encore restarts slskd (changed settings, a new forwarded VPN port, a crash), the session ends without a reason and the next attempt goes as soon as the 30 seconds since the last one allow, without moving the schedule on. After a new password is saved, the attempt waits for the slskd that runs with it.
- **Some answers stop the attempts**: an invalid username or password (the server's words are shown) and a ban stop until the login settings change or an admin presses *Reconnect now*. When another client logs in with the same username, Encore waits 15 minutes and tries once more; if it happens again, it stops too.
- **30 seconds to reach the server** (slskd's `soulseek.connection.timeout.connect`, was 10 seconds). The wait for the login answer (the "5000 milliseconds" in the message) is fixed inside slskd 0.26 and can't be set; `docs/backlog/slskd-upstream.md` asks slskd for a setting.
- **Searches go through one gate**: one Soulseek search at a time (from the request worker, the picker and the Soulseek page alike), each starting at least 3 seconds after the one before, and none while Soulseek is not logged in. A "too many searches" answer pauses searches for 60 seconds instead of failing them (a request's search tries again, up to five times, and the request says "Rate limited by the Soulseek server – searching again at 14:05" meanwhile; a person sees when the next search can go). A person's search goes before the requests waiting for their turn; it waits for the search that is running for at most 30 seconds in all, and behind a request's search that sits out the server's pause it is told at once when the next search can go. A request's search holds the turn for its whole *Search time* (Settings → Downloads → Soulseek, 15 seconds by default): set above about 25 seconds, a person's search that comes while one runs is often refused as busy.
- **Requests wait instead of failing.** While Soulseek is disconnected for a reason worth retrying, a request's Soulseek step parks the request (status `waiting`, "Waiting for Soulseek – next attempt at 14:20"), without counting an attempt, and it goes on where it stopped once Soulseek is back. The same goes while the VPN is down (with the kill switch on), while the Soulseek engine is being restarted, when the session drops in the middle of a search (the cut-short search no longer counts as "no results"), and when it drops while a Soulseek download runs: the transfers end with the session, so the request waits for Soulseek and searches again once it is back, and the user whose transfer ended is not counted as failed. A file picked by hand (the picker, the Soulseek page) waits the same way and is asked for again once Soulseek is back. **A request that has waited 60 minutes goes on to its next source** (YouTube Music, for example), as before, so nothing waits for ever; a picked file, which has no other source, fails then. When Soulseek is off, not installed, or stopped for a reason of the server's (a rejected login, a ban), the Soulseek steps are skipped right away, as before.
- **Retry failed** (and the per-row *Retry*) only puts the requests back in the queue; their Soulseek searches then go through the gate one by one, so retrying hundreds of downloads no longer fires hundreds of searches. A search whose request is cancelled, or whose picker is closed, is stopped in slskd before the next one starts.
- **Downloads are handed to slskd one at a time.** slskd takes two downloads at once and answers a third with "Only one concurrent operation is permitted" (429) while it asks the Soulseek server and the other user's client. Encore now hands them over one by one and asks again 2 seconds after such an answer; when slskd stays busy, the request says "Waiting for Soulseek to take the download from …" and asks for the same files at its next look (for up to 10 minutes) instead of counting that user as failed.
- **The log says what happens, once**: `soulseek: connecting (attempt 3)`, `soulseek: logged in as alice`, `soulseek: disconnected – the login timed out (the Soulseek server did not answer in 5 s); next attempt in 2 m 10 s`, `soulseek: search rate limited – waiting 60 s`, and at most once a minute `soulseek: 37 searches waiting for the connection` (requests waiting for Soulseek and searches waiting for their turn, while it is coming back; not once it stopped for good), instead of a line per refused search.
- **Where to see it**: Settings → Downloads → Soulseek shows, under the engine's line, whether Soulseek is logged in, why not and when the next attempt is ("Disconnected – the login timed out (the Soulseek server did not answer in 5 s). Next attempt at 14:20 (attempt 3)."), how many searches are waiting, and a *Reconnect now* button (greyed for 30 seconds after an attempt). When slskd is restarted or waits for the VPN between two attempts, the card keeps the last reason and the planned time. The top line of the Soulseek page and a *Soulseek* row in Settings → Diagnostics say the same (Diagnostics points at Settings → Downloads → Soulseek instead of "below"), and a search on the Soulseek page or in the picker that has to wait for another one says "Waiting for another Soulseek search…". The desktop app shows the same; the phone app shows the sentence in its Soulseek status line. The times in these sentences and in "Waiting for Soulseek – next attempt at …" are the server's clock (the container's `TZ`); the lines under them count in minutes and seconds.

### For API users and developers
- **New: `GET /api/system/soulseek`** (anyone who may pick downloads): the Soulseek session. `state` is `connecting`, `logged_in`, `disconnected`, `waiting` (a next attempt is planned) or `stopped` (Soulseek is off, its engine is not running, or the server refused); `reason` is `timeout`, `rejected`, `kicked`, `banned`, `rate_limited`, `network` or null; `message` is slskd's or the server's own words; `since`, `next_attempt_at`, `next_search_at` and `last_search_at` are unix times; `attempts` counts the attempts since the schedule last started over; `searches_waiting` counts the requests waiting for Soulseek (while it is connecting or an attempt is planned, not once it stopped) and the searches waiting for their turn; `search_running` says a search holds the turn; `server_connections` and `turned_away` count the connections to the Soulseek server Encore let through and the ones it turned away (slskd's own retries) since the server started; `reconnect_in` is the seconds until *Reconnect now* is allowed; `text` is the sentence the apps show ("Disconnected – the login timed out (the Soulseek server did not answer in 5 s). Next attempt at 14:20 (attempt 3)"). `GET /api/soulseek/status` carries the same object as `session`, and its `error` is that sentence while Soulseek is not logged in.
- **New: `POST /api/system/soulseek/reconnect`** (admins): connect now and start the schedule over; `429` with "Wait N s" (and `wait`) within 30 seconds of the last attempt, `400` while logged in, while an attempt is under way or while the engine is not running.
- `POST /api/soulseek/search` answers `409` when Soulseek is not logged in ("Soulseek isn't connected – next attempt at 14:20") and `429` when the search can't start now (another search held the turn for 30 seconds, or searches are rate limited); the picker's Soulseek search answers the same `429`, and its not-connected answer (`409` with the source's state) now says when the next attempt is.
- **Requests: the `waiting` status.** `status` can be `waiting`, with `wait_reason` `soulseek` (until now a Soulseek wait was `queued` with the Soulseek message), `storage_import` (the files are downloaded and the import waits for the storage) or `storage_download` (the staging folder failed before any file existed), and `next_try_at` (unix seconds). `?status=active` includes it, and the events stream sends `status: "waiting"` with `label: "Waiting"`. Every request row also has `has_files` (downloaded files are kept: the apps offer *Import again*), `kept_path` (where), `error` (the last file or program step that failed: `{step, op, path, to, errno, error, storage, text}`, or null) and `output` (streamrip's output: `{source, url, text, ok, at}`, or null). For other users than admins `kept_path` and `output` are null, `error` is `{storage, text}` in plain words, and the server's folders are left out of `message` and `log`. `has_files` can also be true on a completed link request that kept the files it could not import. `attempts` never grows while a request waits.
- **Requests: rejected downloads.** Every request row has `rejected` (the downloads the audio check turned away, oldest first, at most 3: `{id, source, via, detail, url, file, count, check, reason, heard, text, at, has_file, path}`; `text` is the sentence to show, `heard` what the fingerprint matched, `path` the kept folder for admins only), `anyway` (null, or `{action: "keep" | "download", id, text}`: which button to offer) and `skip_check` (the request runs, or ran and failed, without the audio check).
- **New: `POST /api/requests/{id}/keep-anyway`** and **`POST /api/requests/{id}/download-anyway`** (admins, and the request's owner with the `fix` permission), body optional `{"rejected": <id>}`: `{ok: true, status: "waiting"}` and `{ok: true, status: "queued"}`. Errors are `{detail}` with 400, 403, 404 or 409 ("There is no rejected download to keep", "The rejected download is gone – Download anyway asks for it again", "Ask an admin to keep it anyway", "It is being imported now", …).
- **`POST /api/picker/pick`** takes `no_check: true` ("Don't check the audio"): admins, and members with the `fix` permission; others get 403 "Ask an admin to pick without the audio check". Only the audio check is off; the quality and release checks still apply.
- **`POST /api/picker/search` answers an object** instead of a bare array: `{items, from, cached_at, found, query, can_search, notice}`. `items` are the rows as before; `from` is `"cache"` (a kept search, Soulseek and torznab only) or `"live"`; `cached_at` is unix seconds and `found` the line's words ("Found at 14:02"), both null when live; `query` the words in the search box when the kept search is the one they make, else the words the rows were found with (the apps show them after "for" when they differ from the box), and for a live answer the words sent; `can_search` is false only for kept Soulseek rows while Soulseek isn't connected, and `notice` then says why. It takes `request_id` (the request the picker was opened for; ignored when the caller may not see it) and `fresh: true` (*Search again*: skip what is kept; `409` while Soulseek isn't connected). A Soulseek search while Soulseek isn't connected answers `200` with kept rows, or the `409` as before when nothing is kept. In rows from `torznab`, `payload.url` holds `apikey=encore-seal-<40 hex>` where Prowlarr's key was: send the payload back unchanged with the pick; a changed link isn't given the key.
- **Settings schema**: the section `apps` is gone; `library` (alias `tagging`), `downloads` (alias `apps`), `integrations` (alias `services`) and `processing` take its place, and no group has a `part` heading any more. A name in `#/settings?s=` is looked up as a page id, then an alias, then a group id.
- **New: `GET /api/requests/storage`** (anyone signed in): for admins `{ok, since, checked_at, next_check_at, path, op, error, errno, step, waiting, text}`, for everyone else `{ok, since, text}`; `text` is the banner's sentence, null while imports go on. **`POST /api/requests/storage/check`** (admins): every folder probed now, the answer is the same object; waiting imports go on at once when it passes.
- **New: `POST /api/requests/{id}/import-again`** (the request's owner or an admin): `{ok: true, status: "waiting"}`, or 400 with "Nothing to import – the downloaded files are gone", "There are no downloaded files to import" (a wait for Soulseek), "Only a failed or waiting import can be imported again" or "It is being imported now". `POST /api/requests/{id}/retry` on a failed request with kept files imports them the same way (on a playlist, for each of its songs). `POST /api/picker/pick` with the `request_id` of a request whose files wait to be imported answers 409.
- **Removed routes** (none of the apps called them; a call now gets what any unknown address gets: a `GET` the web app's page, a `POST` 405):
  - `GET /api/system/status`: Settings → Diagnostics (`GET /api/system/diagnostics`, admins) checks the outside services, the folders and the tools; `GET /api/system/tools` and `GET /api/system/vpn` have the tools and the VPN.
  - `GET /api/roon/status`: use `GET /api/roon/zones`.
  - `POST /api/sync/all`: the scheduled sync (`ENCORE_SYNC_INTERVAL`) still covers every account, and `POST /api/sync` syncs your own connections.
  - `GET /api/admin/activity`: the same answer is at `GET /api/system/activity`.
  - `POST /api/library/tracks/{id}/verify`: `POST /api/library/verify` checks the library.
  - `GET /api/auth/invite/{code}`: an invite code is checked when it is used, by `POST /api/auth/signup`.
- `GET /api/system/downloads` no longer has the `"lidarr"` list, which was always empty.
- **Stream headers**: a stream now carries only `x-encore-stream` (the same words as before: `original`, `flac`, `flac-fallback`, `aac-<kbps>`, `opus-<kbps>`, `cadenza-<rate>`) and, on the original file, `Vary: X-Encore-Decoders`. The four other headers are gone: `x-transcoded` (the same word as `x-encore-stream`; the phone app only read it from servers older than 0.27), `x-cadenza-path`, `x-encore-dsp` and `x-encore-dsp-offset`. No app read the last three.
- **New: `output_rate`** in the answer of `POST /api/playback/dsp/prepare`: the sample rate (Hz) the server's Cadenza processing sends for that song, also when the render cache is off. The apps still work it out themselves for now.
- **New: `GET /api/admin/perf`** (admins only): the last 500 slow requests (250 ms or more), the number of calls with p50, p95 and the slowest per route, the size of the server's caches, the waits for a database connection and how old the background copies are. A request that takes 250 ms or more is also written to the log (`slow request: GET /api/... 200 312 ms`).
- **New: `GET /api/admin/settings/schema`** (admins only): every server setting the Settings pages show, grouped into pages (`sections`) and cards (`groups`), each field with its key, label, help, type (`text`, `password`, `number`, `bool`, `select`, `checks`, `textarea`, `path`, `url`), options, `when` rule, whether it is secret or set by an environment variable (and which), its default, unit and limits. No values; those stay at `GET /api/admin/settings`. `docs/contracts/settings-schema.md` describes it.
- **The server is a Cargo workspace.** `server/src/main.rs` is the `encore` binary and only wires the parts together; everything else is in `server/crates/` (`core`, `db`, `config`, `http`, `media`, `library`, `requests`, `playback`, `sync`, `jobs`, `vpn`, `system`, `api`). `cargo test --workspace` in `server/` runs every crate's tests and `server/tests/`, which call the server through its router with the `TestServer` helper. The database migrations are numbered files in `crates/db/migrations/` (the schema version stays 26). Every setting is one entry in `crates/config/settings.toml`, from which the build makes the defaults, the typed accessors and the schema above. The README's Development section has the layout.
- The speed table is `cargo bench --bench perf` (it was a test, `perf_bench`). The x86_64 build of a release prints it into the job summary; for a pull request, start the test-and-build workflow by hand to get it.
- The release binary is built as one optimised unit (`lto = "fat"`, `codegen-units = 1`): it takes longer to build. How much faster it runs than 0.28's profile was not measured on its own (`docs/perf/0.29.md` compares whole versions).
- Panics still unwind: `panic = "abort"` was considered and not taken. The database lends its connections under a panic guard, and a panic in one request or background task fails only that request or task; with abort, any panic would stop the whole server.
- **CI** runs the server's tests and `cargo clippy -- -D warnings` for every crate (the server was not linted before), and `scripts/check-cadenza-pins.sh`, which lists where Cadenza is pinned and fails when the server, the desktop app and the phone are not on the same rev (not blocking yet: the desktop app is ahead of the other two).
- The Docker image builds the whole workspace; nothing changes in how it is run.
- `scripts/release-apps.sh --android` builds the native Android app in `clients/android` with Gradle, as the apps workflow's `android-native` job does (the Android SDK and NDK, cargo-ndk, Gradle and a JDK; an APK that is uploaded must be signed with the release key). The Tauri Android build and the apps workflow's `android` and `desktop-classic` jobs are gone with `clients/app`.

### What to test
- **Storage problems** (the main point of this release): make the library read-only for a minute – `chmod a-w` is not enough (that is "Permission denied", which Encore treats as a permission problem, not a storage one); use a read-only bind mount over the library folder (or `:ro` on the volume and recreate the container). Then pick an album: the request shows *Waiting* with the folder, the operation and the error; the banner shows on Requests and on the Downloader page (as an admin with the path and *Check again*, as a member in plain words); *Check again* says "Imports are still paused"; the request's details show everything and *Copy* puts it on the clipboard; `docker logs` has the storage line. Make the library writable again and press *Check again*: "Imports resumed", the banner goes, the request completes, *Attempts* did not grow, and nothing was downloaded twice (one streamrip run in the details' output and in the log). Restart the container while a request waits: it still waits, and imports once the library can be written.
- **Keep anyway**: a request whose download the audio check turns away (a song the check gets wrong, or a nightcore copy titled without the word): it shows the reason in full and *Keep anyway*; press it, and the song is imported and shows "✓ confirmed" in the library; the verification task leaves it alone. Then *Download anyway* on a request whose kept file was deleted, and a pick with *Don't check the audio* on. As a member without *Fix their own downloads*: the reason shows; Keep anyway, Retry, *Retry failed* and the picker's switch don't. Keep anyway on a file the quality check fails (with *Check every download before it enters the library* on, Settings → Blocked): the request fails with the quality reason. A title with "(nightcore)" or "(sped up)": its log says it was checked by length and title only.
- **Kept searches**: open the picker for a Soulseek album, close it and open it again: "Found at …" shows at once and slskd's log has no second search; *Search again* runs one. Stop Soulseek: the kept rows still show with the reason instead of *Search again*.
- **Torrents and Usenet**: with Prowlarr and qBittorrent (or SABnzbd/NZBGet), an album that is not on Soulseek in FLAC: it should reach the indexers before Soulseek MP3s, qBittorrent should get the torrent from Encore, and a queued torrent should wait, not stall (also with Transmission or Deluge). *Test connection* on Prowlarr and SABnzbd. In the picker's Torrents & Usenet tab, a row's link (the browser's network panel) carries `encore-seal-…`, not Prowlarr's key, and picking it still downloads. With a client running as another user than Encore, restart Encore's container: the client can still write to its download folder. An album request whose download is tagged as another album of the artist (with *Tag downloads from MusicBrainz on import* off, so there is no track list) is turned away as the wrong release and the next one is tried.
- **Settings pages**: Library, Downloads, Integrations and Server processing, and an old link (`#/settings?s=apps`, `?s=slskd`, `?s=cadenza`) opening the right page.
- **Import again** on a failed request whose files were kept (a permission problem: `chmod a-w` on the artist's folder does that), after fixing the permission.
- **streamrip**: a Deezer or Qobuz download; its output is in the request's details, `docker logs` shows a line for a source that failed, and with the image's streamrip 2.4.10 no update notice appears in the output.
- **The fixes**: a Tidal search in the picker; *Ke$ha – Cannibal* through torrents; a YouTube link of a song you already have ("Already in your library"); the setting *Staging folder for downloads* in Settings → Library → Library & tagging.
- **Everything you use, as in 0.28**: Home, the albums, artists and songs lists with a few sorts and a search, an album, an artist and a playlist page (also Liked Songs), For you, Requests, a request going through, playing an original and a converted song (the Signal path reads as before), server processing with Cadenza, Your devices, the side bar's counts.
- **Settings as an admin**: every server card; labels, help lines, the choices of a select, fields that only show with another setting (a source switched on), a setting fixed by an environment variable (it names the variable and can't be changed), a password field (masked; empty keeps it), *Save* and the *Test* buttons.
- **Desktop** (with the next app release, which brings the new desktop app): if you still have the classic app, install the new one and sign in; the classic app no longer offers an update.
- **Soulseek**: the Soulseek card's state and reason, and the time of the next attempt while it is disconnected; *Reconnect now* (refused with "Wait N s" right after an attempt); then *Retry failed* on a list of failed downloads while you watch the log: one `soulseek:` line per change, searches one at a time and at least 3 seconds apart, no storm of "429" or "must be connected" lines in slskd's log (on searches and on downloads), and requests showing "Waiting for Soulseek – next attempt at …" while it is disconnected. Restart slskd (or take the VPN down) while a Soulseek download runs: the request should wait for Soulseek and search again afterwards, not go on to YouTube Music. The clock times in the card's sentence and in the requests' messages are the server's: if they are hours off, set `TZ` for the container (docker-compose passes `TZ`, UTC when it is not set). In slskd's log (the engine log on the Soulseek card) a failed attempt may be followed by one "Attempting to connect…" and a "Connection reset by peer" within the same second, then "Reconnection attempt cancelled": that is slskd's own retry being turned away and quieted, and it does not reach the server. `GET /api/system/soulseek` counts the connections that reached the server (`server_connections`) and the ones turned away (`turned_away`): the first should grow only by one per "soulseek: connecting (attempt N)" line. Change the VPN's forwarded port or the Soulseek settings while logged in: Soulseek should be back within about 30 seconds, without a "next attempt in 5 m".
- **Source order**: if yours names `lidarr` or `hifi`, take them out by hand (and put `torznab` where `lidarr` was, if you want torrents tried there); Encore leaves the saved order as it is. Then a request goes through the sources in your order.
