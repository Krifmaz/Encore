## Encore 0.28.0

### The website works offline
- **Download for offline in the browser.** ⋯ → *Download for offline* on a song, an album, a playlist or Liked Songs saves the songs in the browser together with their covers and lyrics; on a saved song the entry reads *Remove download*. A toast counts along ("Downloading 3 of 12 · <title>") and ends with "12 songs downloaded" or "10 downloaded, 2 failed". The original file is saved when the browser plays it; otherwise a 256 kbit/s AAC copy made by the server (Opus where the browser has no AAC decoder), marked "(converted)" in the list, and *Download again in original quality* replaces it once the original can be saved. Two songs are fetched at a time; a song that fails is reported and the others go on, and a full disk says "There is no room left on this device for downloads". Works in Chrome, Brave, Edge, Firefox and Safari (iPhone and iPad too) over HTTPS or on `localhost`: browsers only allow offline storage and service workers on secure addresses, so a plain `http://192.168.1.10:8080` shows no download entries. The apps keep their own *Save for offline*.
- **Downloads** (in the side bar below Library, at `/downloads`): the saved songs grouped by album with their quality and size, a search box, play buttons per album and per song, ⋯ per song (Play, Play next, Add to queue, Remove download), *Remove all*, and a storage line: "<used> of <quota> used · <n> songs · persistent". *Make persistent* asks the browser to keep the downloads when the disk fills up. On an iPhone or iPad in Safari the page, and the first download, say "Add Encore to your Home Screen (Share → Add to Home Screen) and download from there: Safari clears a website's downloads after a week without a visit, and the Home Screen app keeps its own.": Safari deletes a website's storage after 7 days of use without a visit to it; an app added to the Home Screen is spared, but it has storage of its own, so songs downloaded in a Safari tab don't show up in it.
- **Offline mode.** When the server can't be reached (also behind a reverse proxy such as Caddy, nginx, Traefik or Cloudflare that answers with its own error page while Encore is down, and within seconds when the server's address doesn't answer at all) and this browser has downloads and was signed in during the last 30 days, Encore opens anyway: the banner "Offline – the server can't be reached. Downloaded songs play." with *Retry*, the Downloads page, and everything else greyed out ("Not available offline"). Plays and likes are kept on the device and sent when the server is back ("Back online – 3 plays sent"), each play with the time you listened, also to Last.fm and ListenBrainz (Last.fm takes scrobbles up to two weeks old). Encore tries the server again every 30 seconds and whenever the device goes back online. Thirty days after the last time the browser reached the server signed in, the banner asks you to sign in again when the server is back, and downloaded songs stop playing until then. Without downloads or a recent sign-in, the sign-in page's "Can't reach" message stays as before.
- **Downloaded songs play from the device while online too**: Settings → Playback → *Play downloaded songs from this device* (on by default; "Saves data when a song is already downloaded here."). The Signal path then starts with "Source: downloaded copy on this device · FLAC 16/44.1".
- **The interface itself is kept by the browser.** The service worker keeps the app (its code, styles and icons) so it opens without the server and starts faster. When the server has a new version, the page says "A new version of Encore is ready" with *Reload* instead of switching under you mid-song. In the Docker image, the server also sends the app's files pre-compressed (brotli, or gzip), so the first load is smaller.
- **Going back to 0.27 or older deletes the songs downloaded in browsers and the plays and likes not sent yet**: the 0.27 service worker takes over at once and clears every saved copy that is not its own. Open Encore online once before going back, so the plays and likes are sent.

### Updates and restart from Settings
- **Settings → Diagnostics → Updates** (admins only): "Encore 0.28.0" and either "You have the newest version" or "Encore 0.29.0 is available" with the release date, *What changed in 0.29.0* (the release notes as text), *View on GitHub* and *Check now*; the card also names the copy of the app this browser keeps for offline use. The server asks GitHub once a day – the scheduled task *Check for Encore updates*, switched by the `check_updates` setting (`ENCORE_CHECK_UPDATES`, on by default); the GitHub token setting from 0.26.7 is used when set – and keeps the answer, so the Settings page header shows "Encore 0.29.0 is available – Diagnostics" to admins without asking again.
- **Restart server**: after "Restart the server? Playback stops for about ten seconds." the server stops taking new connections, lets open requests finish (up to 10 seconds), writes the database out, stops Soulseek and the translator, ends whatever else it still runs (a download, a conversion, a Cadenza render), and exits with code 75; the page waits for it and offers *Reload* when it is back. In the Docker image the entrypoint now runs the server in a loop: exit code 75 starts it again at once, any other exit code ends the container as before, so `restart: unless-stopped` behaves the same, and `docker stop` still stops it. The Linux and Windows archives have no such loop: *Restart server* ends the process with exit code 75, so a service manager has to start it again – with systemd, `Restart=on-failure` plus `RestartForceExitStatus=75` in the unit.
- **Update now**, only when the Docker socket is mounted: pulls `ghcr.io/krifmaz/encore:<new version>` and replaces the running container with a new one with the same settings (environment, volumes, ports, networks and their aliases, restart policy, labels, devices, limits) under the same name, Watchtower-style. A short-lived helper container from the new image does the swap and prints every step (`docker logs` shows them until it is removed): it stops the old container, renames it `<name>-old-<time>`, creates and starts the new one, and removes the old container (not its volumes) once the new one keeps running; if creating or starting the new one fails, the old one gets its name back and starts again. After "Update to 0.29.0? The container is replaced by a new one with the same settings; this takes a minute." the page asks the server every 2 seconds and shows "Back" with *Reload* once the new version answers ("the update did not go through" when the old one comes back instead); after 90 seconds it says "The server did not come back yet – check `docker ps`". Without the socket the card says why ("The Docker socket is not mounted", "Not running in a container", or the socket is not writable by Encore's user, with the `PGID` to set) and links to the README. `self_update = off` (`ENCORE_SELF_UPDATE=off`) hides the button even with the socket mounted; set as the environment variable, it also keeps Encore's user out of the socket's group, so nothing Encore runs (slskd, yt-dlp, streamrip, Cadenza, the translator) can use the socket.
- Update now works from this release on: 0.28.0 is the first image with the helper in it, so the first update it can do is to the release after this one; older tags are refused. The pull goes through the Docker daemon without registry credentials, so it needs the image to be public on ghcr.io.
- **To use Update now**, mount the socket in your compose file. The socket gives the container control of Docker on this host; mount it only if you want *Update now*:

  ```yaml
  services:
    encore:
      volumes:
        - /var/run/docker.sock:/var/run/docker.sock   # optional: only for Update now
  ```

  Encore runs as `PUID`/`PGID`, so the socket must be writable by that user: when the container starts, the image adds Encore's user to the group that owns the socket on the host. Only a socket owned by root's group (gid 0) is left alone; then the Updates card says the socket is not writable and names the group: set `PGID=0` (the files Encore writes then get that group too), or run with `PUID=0`.

### Fixes

- **Covers no longer flash on pause and play.** Pausing or playing redrew the whole player bar and the full-screen player, so every cover (the big one and each one in Up next) faded in again over its colour. Now a pause or play only changes the button, and a cover already shown on the page appears at once when a view is drawn again (a new song, a queue change).
- **The YouTube sign-in extension looks like Encore** and keeps everything in the popup of its toolbar button (see What to test).

### For API users and developers
- `POST /api/library/plays` also takes a list, `{"plays": [{"track_id", "seconds", "played_at"}]}` or a bare array of the same, up to 500 per call (413 above): each play is saved and scrobbled with its own `played_at` (Unix seconds, clamped to the last 400 days), unknown songs and plays already saved (the same song at the same `played_at`) are skipped, so a list can safely be sent again, and the answer is `{ok, saved, skipped}`. The single form `{track_id, seconds}` is unchanged.
- `GET /api/library/tracks/{id}/info` has `offline_ok` next to `stream`: true when the original file plays in the asking client and can be saved as it is.
- The converted streams (`flac`, `flac-fallback`, AAC, Opus) and the Cadenza stream answer `Cache-Control: private, no-store`; the original file keeps `private, max-age=3600`.
- `GET /api/system/update` (the version check; `?force=1` asks GitHub again), `POST /api/system/update` (`{tag}`, the self-update) and `POST /api/system/restart` are admin-only and need the CSRF header like every other change.
- `docs/contracts/offline-manifest.md` describes the record every client keeps for a saved song (web, desktop, and the phone from 0.30), where each keeps it, and how an older index is read. The desktop app writes it from this release on (the track id as a number, `saved_at` in whole seconds, the quality label, `cover`, `track`, `disc`, `format`, `artists`) and upgrades its 0.27 list when it reads it.

### Not in this release
- **The phone app's offline store, its in-app update and its bug report screen come with 0.30**, the phone release. Until then the phone's browser has the website's offline mode, and the phone app updates from the Releases page as before.

### What to test
- **Brave on the desktop and the phone browser**: *Download for offline* on a song, an album, a playlist and Liked Songs; the Downloads page numbers (used, quota, persistent, *Make persistent*); stop the container and reload: the banner, the Downloads page, play and queue songs, everything else greyed; like a song and play two; start the server again and press *Retry*: "Back online", and the plays (Home's "songs you played", and Last.fm/ListenBrainz with the times you listened) and the like arrive.
- **iPhone Safari**: the Home Screen hint in a Safari tab (on the Downloads page and with the first download); then add Encore to the Home Screen, download from the Home Screen app, and check that those downloads stay and play offline (the ones made in the tab don't show there); Lockdown Mode still shows the WebAssembly message.
- **A song the browser can't play as it is** (ALAC, APE, WavPack, DSD): saved as "(converted)"; *Download again in original quality* is offered on converted copies while online; where the original still can't play, nothing is downloaded, the copy stays and the page says so.
- **The new version message**: keep a tab open while you update the server; it shows "A new version of Encore is ready", and *Reload* opens the new version.
- **Settings → Diagnostics → Updates** on your server: the version line, *What changed*, *Check now*; *Restart server* comes back within about ten seconds; with the socket mounted the card shows no "not available" line (or names what is missing). *Update now* itself can only be tried once the next release is out, since the button shows only for a newer version: then `docker ps` shows the new container under the old name, the old one gone, and your settings, volumes, ports and networks unchanged, and Portainer still manages the stack.
- **Desktop app**: your saved songs are still listed and play; a song saved now shows its quality with bit depth and rate ("FLAC 16/44.1", "MP3 320k"), and one the server converted says "(converted)".
- **The 30-day grace**: after *Sign out everywhere* on another device, this browser's downloads keep playing offline until 30 days after it last reached the server; once the server is back it asks you to sign in.
- **Signing out while the server is stopped**: *Sign out* still works in offline mode and opens the sign-in page. The session can only be ended by the server, so the browser remembers that it signed out: start the server and reload, and it asks you to sign in (it does not open as the user who signed out). Plays and likes waiting from that user are sent under their own session first; another user who signs in on this browser never gets them.
- **The YouTube sign-in extension** (load the new zip): its toolbar button now opens one popup in Encore's charcoal and cream (light when the system is light) with everything in it – *Hand over a YouTube sign-in*, the switch and *Send now* for this browser's own sign-in with the last result ("3 cookies received · today 14:02"), and under *Encore connection* the address and the token (*Show* reveals it). The extension's Options in the browser's extension settings open the same page in a tab. Save a new address in Firefox: its permission prompt closes the popup, and opening the popup again says whether the permission was given and to click the button once more.
- **Covers while pausing**: open the full-screen player with a queue, pause and play a few times: the big cover and the Up next covers stay as they are (before, each one flashed its colour). Skip to the next song: covers already seen appear at once.
