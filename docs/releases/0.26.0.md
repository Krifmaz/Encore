## Encore 0.26.0

### The website is the Rust app
- **The Rust/WebAssembly interface is now the website**, served at `/` (the old `/next/` address redirects there). Same sign-in, same pages, same look; this is where every interface fix in this release landed. The desktop app opens it straight away.
- **`ENCORE_LEGACY_UI=1`** brings the previous JavaScript interface back for this one release only. It has none of 0.26's interface fixes and goes away in 0.27.
- **A browser that blocks WebAssembly gets a message instead of a blank page**, with the steps for that browser: Brave (Shields → allow Scripts for the site), Vanadium on GrapheneOS (Site settings → JavaScript JIT), Safari in Lockdown Mode (aA → Website Settings), Edge with enhanced security (the lock icon → turn it off for the site). With scripts blocked altogether the page says so too.

### Downloads that stopped working
- **Soulseek no longer crash-loops on a folder it can't write to.** The folders you set in the environment (staging, download and blackhole folders) are created and owned by Encore's user when the container starts. When slskd still can't write its downloads folder, the card shows the exact `chown <uid>:<gid> <folder>` line (or "set PUID/PGID") instead of the engine's last words, and Encore uses `<config>/downloads/slskd` in the meantime. Saving a folder setting warns the same way.
- **Start now** on the Soulseek card, and a changed setting starts the engine at once instead of waiting out the back-off.
- **streamrip's config is checked before every run** and written fresh when it doesn't load; the old file is kept as `config.toml.bak-<date>` and your Tidal sign-in, Deezer ARL and Qobuz login are carried over. Your credentials are written into it before every run, so streamrip never gets to ask for them on the server. *Reset streamrip config* (Settings → streamrip) forces a fresh file; Diagnostics has a *streamrip config loads* check.
- **"Deezer needs an ARL cookie – Settings → streamrip"** is what a Deezer request says now, instead of streamrip's interactive prompt text. The whole streamrip output is kept with the request.
- **One row per song, with the attempt count**: a song requested again after a failure reuses its row (the old message goes into the log) instead of adding a duplicate. Web and phone.
- **Download missing** on a playlist reports what happened: "Requested 120 · 600 already in progress · 64 couldn't be requested (why)", and each missing row shows its request status. A song whose request vanished or failed is requested again; one that is already in progress is linked to the existing request instead of skipped.

### YouTube: hand over a sign-in
- **0.25.2's guided sign-in is withdrawn.** It asked for your Google email, password and code in Encore's own boxes and typed them into a browser on the server; Google refuses sign-ins made that way, so it is gone, together with the *Browser for YouTube sign-in* download tool from 0.25.0 (an installed copy and its profile are deleted once at start). Nothing of it is kept.
- **What replaces it: the browser extension hands over a sign-in.** Settings → Apps & sources → YouTube sign-in → *Connect the browser extension* gives a one-time token; install `Encore-youtube-extension-<version>.zip` (Chrome, Edge, Brave: Load unpacked → the `chrome` folder, then Allow in Incognito; Firefox: Load Temporary Add-on → `firefox/manifest.json`, then Run in Private Windows), enter your Encore address and the token, press **Hand over a YouTube sign-in**. A private window opens at Google's sign-in; once YouTube Music shows you signed in, the extension sends that window's cookies to Encore and closes it without signing out. The session now belongs to the server alone and is refreshed every 4 hours, also while your computer is off.
- **The card answers at once**; the Google account name shows up a moment later, once Encore has looked it up.
- **Refreshes look like your browser**: Encore renews the cookies presenting itself as the browser the hand-off came from, not as a fixed Chrome.
- **Honest refresh status**: when Google sends no renewed cookies back, the card says "the last refresh renewed no cookies (Google sent none back) – only the sign-in was checked", *Last refresh* stays where it was, and *Refresh now* says "Still signed in – Google sent no renewed cookies, so nothing was refreshed". A renewal that fails while the sign-in still holds shows its reason and is retried in 30 minutes.
- **One name for the everyday sync**: the extension's optional sync of your own browser is called *Everyday browser (extension)* everywhere; Encore never refreshes those cookies. Pasted cookies stay the backup.
- For API users: the old `managed` name, `next_check` in the status and the old-browser clean-up still work in 0.26 and are removed in 0.27.

### Speed
Measured with the server's own bench on a 60 000-song library (full table in `docs/perf/0.26.md`, baseline in `docs/perf/0.26-baseline.md`). Warm median, before → after:

| Call | 0.25 | 0.26 |
|---|---|---|
| Requests page (`/api/requests`) | 19.9 ms | 10.5 ms |
| Home: your stats (`/api/stats/me`) | 24.9 ms | 19.7 ms |
| Leaderboard | 4.0 ms | 2.8 ms |
| Liked Songs (2 400 songs) | 102.9 ms | 96.9 ms |
| Home page, 6 calls at once | 22.7 ms | 20.4 ms |

- **Songs list pages are slices of one sorted list** instead of a sort per page: the first visit to a page of the Songs tab no longer walks the whole table (ten never-opened pages take 135 ms in total through the API). Pages you already opened load as before.
- **Shuffle** draws random songs from that list instead of sorting every song at random.
- **Six indexes** for requests, playlists, plays and the artist lookup; the database is analysed after the upgrade and optimised after every scan; a bigger statement cache per connection; the write-ahead log is capped at 64 MB.
- **Less work per call**: the list caches no longer drop on unrelated writes (only changes to songs and artist aliases drop them); the translation layer does nothing while nobody has translations on, and skips two queries per call when someone has; the cover pass after a scan runs only when the scan changed something. Every small call is a fraction of a millisecond faster.
- **Read connections** (`ENCORE_DB_READERS`, 4 by default) let pages load while a scan or an import writes. They stay off by themselves when `/config` is on a network file system (NFS, SMB/CIFS, FUSE), with a line in the log; set the variable to turn them on there anyway. Documented in the README and docker-compose.yml.
- **Settings → Diagnostics → Server** says what the box is: CPUs, memory (the container's limit when there is one), whether /config and /music are local or network file systems, the database size, whether anyone has translations on, the read connections in effect. *Copy report* includes it.
- Cold numbers (700–1 100 ms on the first request after start) are the artist index being built; that and the big-payload calls are the structural work planned for 0.29.

### Picker
- **Every source has a tab**: Soulseek, Prowlarr, Qobuz, Tidal, Deezer, YouTube Music. One that is signed out, not connected, not installed or switched off says so in the tab ("Tidal · sign in") with a link to its settings instead of disappearing.
- **Qobuz and Tidal are searched** with the account streamrip is signed in with (Tidal with your developer Client ID when one is set). Qobuz shows the exact bit depth and rate ("FLAC 24/192", "FLAC 16/44.1"); Tidal shows its tier (FLAC 24-bit, MQA, FLAC 16/44.1, AAC). Picks download through streamrip like Deezer.
- **Deezer only searches with an ARL set**; without one the tab says to sign in.
- **"Soulseek isn't connected yet – Settings → Soulseek"** when slskd has no connection, per source; the other sources' results still come back.
- **Lidarr remnants removed** from the picker. Phone the same; its settings links open the server's settings page.

### Artist pages
- **Request discography is a dialog of the releases on the page**, grouped by type (Album, EP, Single, Live, Compilation, Remix …) in the page's order, with a box per release and its year. The boxes start ticked for what Release types allows and isn't owned or requested yet (owned and requested ones are greyed, a skipped one says why – "Live – off in Release types"); *Select all / Deselect all* per group and overall; the button reads **Request N releases** and counts as you tick; only the ticked releases are requested. The phone's sheet does the same.
- **Tap an artist on the phone**: Discover, For you, search, album and player taps look the catalogue artist up with a "Looking up <name>…" hint, fall back to the library artist page when the lookup fails or takes more than 8 seconds, and open the library page at once when the phone is offline. The Library tab's own artist grid keeps opening the library view.
- For API users: the artist request body accepts `release_ids`; `/api/discover/artist/{mbid}` and its `/catalog` carry `kind` and `allowed` per release, and `/catalog` also returns the groups. `release_filter` still works.

### More
- The database moves to **schema 26** (backed up first, as always). The indexes an earlier build added without a schema bump get their backup this way too.

### Install
- **From the next release the desktop app comes as an installer**: `Encore-Installer-<version>-windows-x86_64.exe`, `-macos-universal.dmg` and `-linux-x86_64.AppImage` (or `encore-installer_<version>_amd64.deb`) – [Omnistall](https://github.com/Krifmaz/Omnistall) branded for Encore. One Install button; it downloads the app for your computer from the release, checks it against `SHA256SUMS`, installs it for your user with the shortcuts you tick, and run again it offers Update, Repair or Uninstall. The plain files (`Encore-Setup-<version>.exe`, the `.dmg`, the `.AppImage`/`.deb`/`.rpm`) stay attached under "Files the installer downloads". 0.26.0 itself ships the plain files only.
