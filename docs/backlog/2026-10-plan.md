# Encore rewrite plan (October 2026)

Written Oct 17, 2026 for the review on Tue Oct 20, 9 AM ET. Sources: docs/backlog/2026-10-rewrite.md and the nine
read-only audits of the tree at HEAD c1fefff (server structure, server performance, the 0.25.3 WIP, the two web UIs,
Android, desktop, server-side Cadenza and the device protocol, ops and tools, and the cross-cutting backlog map).
Nothing has been built or started; nothing starts until you say go.

Sizes come from the audits (S about half a day, M a day, L two to three days, XL a week, for a strong agent team)
converted to hours of agent work: S 4, M 8, L 20, XL 40. Calendar time assumes two agent streams in parallel (server
and web in one, phone and desktop in the other), about 16 agent-hours per working day, phases back to back, and two
working days of your testing after each release.

## 1. What changes for you

1. The app looks and behaves as it does now: same pages, same words, same settings keys, same API and database. Where a release changes how a page is built, its text and DOM are checked against the current UI before it ships.
2. The web UI at the normal address becomes the Rust/WebAssembly one; the JavaScript UI is retired (kept behind a switch for one release). A browser that blocks WebAssembly gets a message that says how to allow it for the site.
3. The first release fixes the daily-use bugs (Soulseek folder crash, streamrip config and Deezer ARL, "Requested 0" on Download missing, Tidal and Qobuz in the picker, the discography dialog) and finishes the YouTube hand-off, the speed pass (with numbers) and artist links.
4. On the desktop, Cadenza stops being a device in the picker and becomes "Play through Cadenza on this device" in Settings → Playback, with output, exclusive mode and DSP settings, clear errors instead of a silent "Shared", and lossless FLAC from the server when the engine cannot decode a file (your Opus case).
5. The website works offline with downloaded songs; the phone gets every Settings tab including the admin ones; Settings gets a Plugins tab where tools, connections and the Cadenza engine are installed, updated, disabled, uploaded or fetched from a URL; admins get a file manager.
6. The server is reorganized into crates with the dead code gone, and the 57k-track slowness is measured and fixed with a benchmark whose table ships with every release.
7. Phone, car, web and desktop get volume normalization, the lyrics mode and the artist page sections; the car gets the artist action and the quality badge.
8. Stays the same: your settings and database (migrated in place, backed up before every upgrade), your library layout, the extension, the Android app id, the standalone Cadenza on the LAN as a device, and the release numbering (next is 0.26.0).
9. The plugin catalog ships what Encore has today, all "available, not installed": yt-dlp, streamrip, slskd, Cadenza server processing, the translator, Torznab/Newznab with the torrent and Usenet clients, and the Jellyfin, Plex and Navidrome connections. gamdl and zotify are not in it: both exist to pull music out of DRM-protected streaming services, and this plan does not include writing or shipping plugins for that. The upload and URL install path is generic, so a plugin that follows the manifest can be installed on your own server.
10. Eight releases, 0.26 to 0.33, about 15 working weeks of agent time plus your testing between them.

## 3. Phases

Where this order differs from the suggested one, and why:

- The Rust UI takes over at `/` in the first release (0.26) instead of the third. Every UI fix in 0.26 would otherwise be written twice (JavaScript and Rust) to keep the two UIs in lockstep, the Cadenza redesign in 0.27 is work inside the Rust player, and the desktop app's "is this Encore" check and the service worker have to change with the switch anyway (web audit 4.0, desktop audit section 2, backlog map "R1 first"). The JavaScript UI stays in the image for one release behind `ENCORE_LEGACY_UI=1` and is deleted in 0.27.
- The offline website gets a release of its own (0.28) since the web switch moved out of it.
- "Android full Settings + car items + lyrics mode + normalization + artist page sections" is split in two (0.30 Settings, 0.31 player features): together they are about 220 hours, almost all phone work, and the Settings tabs are a long test on their own. The phone is restructured in 0.30 before features land on it in 0.31.
- "Plugins tab + admin file manager" is split in two (0.32, 0.33): both are server-heavy XL items; one release would hold plugins back by the file manager's server time, and the ops audit names the plugin core as the critical path.
- Numbering stays at 0.26 onward: the newest release notes are 0.25.2 and the WIP commit calls itself 0.25.3; the "0.26.1" in item 9 is slskd's version, not Encore's. The 0.25.3 work ships inside 0.26.0 and its notes retract 0.25.2's guided sign-in.

## 5. Risks

1. Nothing has been built since the WIP commit, which calls itself "may not build". Mitigation: the first task of 0.26 is a clean build and test run of all four trees in CI; every estimate here assumes CI compiles (this container has about 2 GB free and cannot).
2. The YouTube hand-off premise is unproven: a session taken from your private window is refreshed from the server with a fixed Chrome 141 User-Agent from another IP every 4 hours, and a 200 with no Set-Cookie is counted as "rotated". Mitigation: send the agent string the extension reported, say plainly in the status when nothing rotated, keep the pasted-cookie and everyday-extension sources as fallbacks, and judge it after days of your real use.
3. The Rust UI's runtime behaviour is unverified; parity was checked on strings and DOM tokens, not by running it. Mitigation: the legacy switch for one release, Playwright with DOM snapshots, the strings test, and your daily use on 0.26 before anything else lands on it.
4. The Cadenza seam in the web player changes the playback architecture inside the largest client file. Mitigation: split player.rs first, keep the switch off by default, copy the shape of the existing offline player that already drives the engine locally, run the desktop tests in CI, and check linking, remote and the Signal path explicitly in 0.27.
5. The Windows audio fixes need your hardware and live mostly in another repo. Mitigation: Encore shows only what the engine reports, the prompt is written at the start of 0.27 so the Cadenza agent works in parallel, the UI is built against the described state JSON, and 8h lists what only your DAC chain can confirm.
6. The speed complaint has an unknown bottleneck mix (CPU count, disk, translations on, reverse proxy, background tasks). Mitigation: the measured baseline in 0.26, the timing layer and `/api/admin/perf` in 0.29, the bench before and after `ANALYZE` (it can change plans for the worse), and question 6.
7. Replacing the two body-rewriting middlewares moves where `cover_v`, `cover_color`, `artists`, `_t` and `_r` come from; every client reads them. Mitigation: byte-identical JSON fixtures, the existing covers, index and translate tests, and the bench.
8. Schema changes and rollback: an older image refuses a newer database by design. Mitigation: automatic backup before upgrade, your manual backup, at most one bump per release, numbered migrations, upgrade tests from a 0.25 copy, restore steps in the notes.
9. The plugin sandbox is best-effort inside Docker (no per-plugin uid after setpriv, bubblewrap needs the host's seccomp to allow user namespaces) and upload is an admin code-execution surface by design. Mitigation: manifest validation, sha256, trust levels, strict defaults for third-party plugins, no shell templates, the sandbox level shown on the card, and documentation of the compose option.
10. The clients are built only in CI, Android Auto behaviour (icon-only actions, a fifth action, the artist node) is visible only on a head unit, Media3 and Compose APIs drift on every bump, and the three offline stores can diverge. Mitigation: the schema-driven renderer instead of a fourth hand-written Settings copy, the Desktop Head Unit for Auto, the offline contract written before any store, and CI per PR.

Also noted, below the top ten: the Tidal and Qobuz searches of item 12 depend on third-party APIs that may refuse your server's address (the picker states and wording land first and do not depend on them); the hourly cover pass and the share-video builder are CPU-heavy outside the busy gate until 0.29; the heartbeat fan-out grows with devices until the SSE deltas land in 0.29.

## 9. Android review notes (Oct 17), folded into 0.30

- Media3 `MediaLibraryService` (EncorePlaybackService) stays the core; `androidx.car.app` only for the Encore Lyrics screen. No change.
- JNI: `nativeProcess` passes `FloatArray` copies each buffer. In the 0.30 phone restructure, switch to direct `ByteBuffer`s (GetDirectBufferAddress) in `EffectsAudioProcessor` and `cadenza/rust/src/lib.rs`, no per-call copies. Keep plain JNI (nine functions); UniFFI not needed.
- 16 KB page size: NDK 29 + cargo-ndk align by default. Add `-Wl,-z,max-page-size=16384` explicitly to the cadenza crate's Android link flags; in apps.yml fail the build if `llvm-readelf -l` shows any LOAD segment of a `.so` aligned below 0x4000, and run `zipalign -c -P 16 -v 4` on the final APK (0.30, or earlier with any APK release).
- JNI in place: `GetDirectBufferAddress` on the direct `ByteBuffer` gives Rust a `&mut [f32]` over the same memory, so Cadenza processes in place (output written back into the buffer, or into a second direct buffer the Kotlin side owns when the frame count changes with upsampling).
- ABIs stay arm64-v8a and armeabi-v7a; add x86_64 only if emulator testing is wanted.
